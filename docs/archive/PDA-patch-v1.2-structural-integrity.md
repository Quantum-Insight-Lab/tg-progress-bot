## 9. Инварианты сборки

### 9.1 Что не покрыто версией 1.1

Версия 1.1 фиксирует, **что система обязана делать**: граф домена, законы домена, константы, событийное ядро. Этого достаточно, пока исполнитель один — целостность реализации держится в голове архитектора и никуда оттуда не девается.

Как только над одной кодовой базой работают два и более исполнителя (человека или AI-агента), появляется класс расхождений, который методология не ловит:

- оба соблюдают все инварианты домена и при этом пишут два разных способа обработки ошибок;
- появляются две проекции под один и тот же запрос, обе корректные;
- появляются `TaskCompleted` и `TaskDone` — два имени одного факта;
- доменное правило просачивается в контроллер, потому что «так быстрее», и тесты домена этого не видят;
- один агент чинит слой, другой в это же время строит на нём.

Ни одно из этих расхождений не является нарушением инварианта домена. Тесты зелёные. Система при этом расслаивается.

**Тезис патча:** у кодовой базы есть собственные законы, отдельные от законов домена. Они подчиняются тому же правилу раздела 8: *инвариант без механизма обеспечения — это пожелание.*

### 9.2 Новое понятие

| Термин | Смысл | Отличие от инварианта домена | Артефакт/реализация |
| --- | --- | --- | --- |
| **Инвариант сборки** (structural invariant) | То, что должно быть истинно всегда в структуре кода, независимо от того, кто и чем его писал. | Инвариант домена защищает корректность фактов. Инвариант сборки защищает единственность и направление механизмов. | Статические проверки в CI, реестры, генерация типов, линтер-границы. |

Инвариант сборки — не стилистика и не «код-стайл». Проверка формата не относится к этому классу. Относится только то, нарушение чего приводит к расхождению реализаций или к обходу домена.

### 9.3 Каталог инвариантов сборки

Минимальный набор для проекта на TypeScript с событийным ядром. Каждый пункт — с механизмом; пункт без механизма в реестр не вносится.

| ID | Инвариант | Что ломается без него | Механизм обеспечения | Где проверяется |
| --- | --- | --- | --- | --- |
| S-1 | Domain Layer не импортирует API/UI/инфраструктуру | доменные правила уезжают в контроллеры, домен нельзя переиспользовать и тестировать | `dependency-cruiser` или `eslint-plugin-boundaries`, правила по слоям из 4.2 | CI, блокирующе |
| S-2 | Контексты общаются только через события; прямых импортов между контекстами нет | контексты срастаются, деление работы между исполнителями перестаёт работать | те же правила границ, отдельная зона | CI, блокирующе |
| S-3 | Каждый `event_type` существует в реестре событий; типы генерируются из реестра | два имени одного факта, расхождение схем, дубли в проекциях | Event Registry (9.4) + кодогенерация + запрет строковых литералов в `emit` | CI, блокирующе |
| S-4 | Один механизм на одну задачу: один клиент БД, одна точка конфигурации, один способ ошибок, один HTTP-клиент | дрейф реализаций; каждый следующий агент копирует ближайший образец | реестр механизмов в rules-файле + тест-перепись (счётчик реализаций) | CI, блокирующе |
| S-5 | Запись и чтение разделены: проекция не пишет в Event Core | тихая порча инвариантов домена (антипаттерн раздела 8) | правило границ на директорию проекций | CI, блокирующе |
| S-6 | Нет циклических зависимостей между модулями | порядок сборки становится неопределённым, рефакторинг блокируется | `madge --circular` | CI, блокирующе |
| S-7 | Каждый инвариант домена имеет тест, ссылающийся на его ID | инвариант остаётся текстом в спеке | нейминг-конвенция `INV-xx` в названии теста + скрипт сверки со Invariant Spec Sheet | CI, блокирующе |
| S-8 | Константы (раздел 5.4) читаются только из конфигурационного слоя | числа расползаются по коду, калибровка становится невозможной | запрет магических чисел в домене (линтер-исключение по списку) | CI, предупреждение → блок |
| S-9 | Мёртвый код и неиспользуемые экспорты не накапливаются | агенты дублируют то, что уже есть, но не видят | `knip` | CI, предупреждение |

Правило внесения: инвариант сборки принимается в реестр только вместе с работающей проверкой. Пункт «договорились так делать» в реестр не попадает — он попадает в rules-файл (9.5), а это другой уровень надёжности.

### 9.4 Event Registry

Единый файл — источник правды по событиям. Заменяет ситуацию, когда каталог событий живёт в документе, а имена — в коде.

Формат (пример структуры записи):

```yaml
- type: TaskCompleted
  version: 1
  context: tasks
  actor: user
  subject: Task
  payload:
    task_id: string
    completed_at: timestamp
  idempotency_key: "task_id + completed_at"
  invariants: [INV-03, INV-07]
  projections: [today_list, weekly_digest]
  owner: max
```

Требования:

1. Из реестра **генерируются** типы событий и схемы валидации (Zod или аналог). Ручное объявление типа события — ошибка сборки.
2. Добавление события — отдельный PR, не смешанный с реализацией фичи. Ревьюит архитектор.
3. Изменение схемы существующего события — только через `schema_version + 1`; правка версии 1 запрещена, потому что в Event Core уже лежат факты.
4. Каждое событие обязано указывать связанные инварианты. Событие без инвариантов — сигнал, что закрываемая неопределённость не сформулирована (раздел 3, шаг 1).

### 9.5 Контракт агента (Agent Rules File)

Файл в корне репозитория (`AGENTS.md` / `.cursorrules`), который агент читает перед каждой задачей. Это преимущество AI-исполнителей перед людьми: инструкции соблюдаются буквально и не устают.

Обязательные разделы файла:

| Раздел | Содержание | Зачем |
| --- | --- | --- |
| Карта слоёв | что где лежит, направление зависимостей (из 4.2) | агент не изобретает структуру |
| Реестр механизмов | конкретные имена: клиент БД, логгер, конфиг, обработка ошибок, HTTP-клиент — «использовать только эти» | закрывает S-4 на входе, до CI |
| Запреты | новый event_type без реестра; доменное правило вне домена; новая зависимость без согласования | закрывает типовые расхождения |
| Порядок работы | сначала спека (этап 1 PDA), потом код (этап 2); спека содержит затрагиваемые инварианты | сохраняет двухэтапность |
| Definition of Done | тесты на затронутые инварианты, обновление реестра событий, проверки CI зелёные | не даёт «почти готово» |
| Что делать при конфликте | если задача требует расширить граф домена или добавить событие — остановиться и запросить решение, не изобретать | защищает домен от тихого расширения |

Rules-файл — не замена проверкам из 9.3. Он снижает частоту нарушений, CI её обнуляет. Одного rules-файла недостаточно: это тот самый «инвариант как договорённость».

### 9.6 Организация параллельной работы

**Деление работы.** Задачи распределяются по bounded context (колонка «Владелец» в Domain Graph Canvas, раздел 5.2), а не по фичам. Один контекст — один исполнитель на отрезке времени. Фича, проходящая через два контекста, режется по границе событий: исполнитель A публикует событие, исполнитель B на него подписывается. Контракт события согласуется до старта обоих.

**Общее ядро.** Event Core, Domain Layer общих сущностей и Stability Engine — зона архитектора. Изменения туда идут отдельными PR и не выполняются агентами параллельно.

**Протокол расширения графа.** Расширение графа домена, новый тип связи, новое событие — решение архитектора. Агент, упёршийся в это, останавливается и формулирует запрос, а не достраивает домен самостоятельно.

**Узкое место.** В версии 1.1 роли архитектора, доменного эксперта и техлида описаны как разные. Если все три совмещены в одном человеке, при двух и более исполнителях он становится узким местом: каждое расширение графа ждёт его. Это нормально при одном исполнителе и деградирует при масштабировании. Измеряется метрикой «lead time расширения графа» (9.9); если она растёт — либо часть решений делегируется, либо часть контекстов замораживается по составу событий на период спринта.

### 9.7 Артефакт: Structural Invariant Sheet

Шаблон по образцу 5.3, для инвариантов сборки.

| Поле | Значение |
| --- | --- |
| ID (S-xx) | ... |
| Формулировка (одной строкой) | ... |
| Что ломается без него | ... |
| Механизм обеспечения (конкретный инструмент и правило) | ... |
| Где проверяется (pre-commit / CI / оба) | ... |
| Режим (предупреждение / блокирующе) | ... |
| Как выглядит нарушение (пример кода) | ... |
| Легальные исключения и как они оформляются | ... |
| Владелец | ... |

Поле «легальные исключения» обязательно. Инвариант сборки без описанного способа исключения либо будет обойден молча, либо остановит работу на первом же оправданном случае.

### 9.8 Дополнения к чек-листам раздела 7

**К 7.1 (продуктовый дизайн):**
- Определены bounded contexts и их владельцы; для каждой пары смежных контекстов названы события на границе.

**К 7.2 (инженерная реализация):**
- Заведён реестр инвариантов сборки; каждая запись имеет работающую проверку в CI.
- Правила границ слоёв и контекстов выполняются автоматически, а не на ревью.
- Event Registry — единственный источник имён и схем событий; типы генерируются.
- Каждый инвариант домена имеет тест, ссылающийся на его ID; расхождение спеки и тестов ломает сборку.
- В репозитории есть Agent Rules File с реестром механизмов и Definition of Done.

**К 7.3 (запуск и эксплуатация):**
- Введена метрика покрытия инвариантов механизмами; отслеживается разрыв между спекой и CI.
- Определён порядок изменения общего ядра при нескольких параллельных исполнителях.

### 9.9 Дополнения к разделу 8 (антипаттерны)

| Антипаттерн | Почему это ломает систему |
| --- | --- |
| Два исполнителя на одном контексте | Границы контекста были единственным механизмом развязки; без них конфликт переносится в код и обнаруживается на merge. |
| Инвариант живёт в спеке, а не в тестах | Целостность держится на памяти архитектора. Работает при одном исполнителе, отказывает при двух. |
| Rules-файл вместо проверок | Инструкция снижает частоту нарушений, но не гарантирует их отсутствие. Без CI это договорённость. |
| Архитектор как единственная точка сцепки | Пока все решения о домене идут через одного человека, добавление исполнителей увеличивает очередь, а не скорость. |
| Ревью только через CI | CI ловит нарушения известных инвариантов. Новый класс расхождения он не видит: его сначала нужно заметить человеку и превратить в правило. |
| Имя события придумано на месте | Реестр перестаёт быть источником правды в тот момент, когда в коде появился первый литерал мимо него. |

### 9.10 Дополнения к приложению A2 (метрики)

Слой «Сборка»:

- **Structural coverage** — доля инвариантов домена, имеющих тест: `тесты с ID / инварианты в спеке`. Целевое значение 100%, отклонение — долг.
- **Boundary violations** — число попыток нарушить границы слоёв/контекстов за период. Отличается от инцидентов: это отклонённые попытки, показывают, где граница проведена не по реальному шву.
- **Duplicate implementations** — число механизмов, реализованных более одного раза. Ловит дрейф до того, как он закрепится.
- **Registry drift** — число `event_type`, встречающихся в коде мимо реестра. Норма — ноль.
- **Graph change lead time** — время от запроса исполнителя на расширение графа до решения архитектора. Метрика узкого места, а не кода.

### 9.11 Порядок внедрения

Патч не внедряется целиком. Порядок — от того, что ломается первым.

**Первый день (минимальный набор, три пункта):**
1. S-1 и S-2 — правила границ в CI. Один конфиг, блокирующий режим сразу.
2. Event Registry + генерация типов + запрет литералов (S-3).
3. Agent Rules File с реестром механизмов и Definition of Done.

Этого достаточно, чтобы два агента не расходились по существу.

**Первая неделя:**
4. S-7 — сверка инвариантов домена с тестами. Сначала аудит (приложение П1), потом блокирующий режим.
5. Деление задач по контекстам, протокол расширения графа.

**Дальше, по мере появления боли:**
6. S-4 (тест-перепись), S-5, S-6, S-8, S-9.
7. Метрики слоя «Сборка» на дашборд устойчивости (5.7).

Правило остановки: пункты 6–7 не начинаются, пока 1–5 не работают в блокирующем режиме. Расширение реестра инвариантов сборки без механизмов возвращает методологию к состоянию «пожелания» и обесценивает патч.

## Приложение П1. Стартовый аудит (около часа на проект)

Проводится один раз перед внедрением, даёт цифры для решения о приоритете.

| Вопрос | Как считать | Что означает результат |
| --- | --- | --- |
| Сколько инвариантов домена сформулировано? | подсчёт по Invariant Spec Sheet | меньше 5 — домен не описан, патч преждевременен |
| Сколько из них имеет тест? | ручная сверка | разрыв = объём долга по S-7 |
| Сколько `event_type` в коде? Сколько в документе? | grep по emit/handler | расхождение = масштаб проблемы S-3 |
| Есть ли импорты из домена в инфраструктуру? | `dependency-cruiser` в режиме отчёта | число нарушений S-1 на старте |
| Сколько реализаций у обработки ошибок, конфига, клиента БД? | ручной просмотр | больше одной — дрейф уже начался |
| Сколько времени в среднем ждёт исполнитель решения по домену? | по истории задач | базовая линия для graph change lead time |

Результат аудита фиксируется как единственная строка: **N инвариантов в спеке, M в тестах, K событий мимо реестра.** Это исходная точка, к которой возвращаются через месяц.
