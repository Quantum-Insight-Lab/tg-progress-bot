# Прогресс-бот — редакция 2

Редакция 1 — [`Прогресс-бот.md`](Прогресс-бот.md). Там каждая задача обязана ссылаться на issue, и из этого issue берутся этап, исполнитель по умолчанию, порядок плана, сигнал «похоже, готово», застой и список issues без задач.

Редакция 2 этот стык убирает. Задача — шаг, который человек ведёт в Telegram. GitHub — зеркало репозитория: issues, PR, коммиты, CI, milestones. Общее между ними два: человек (аккаунт Telegram и логин GitHub) и проект (к нему подключён репозиторий). Issue не является родителем задачи и не каталог, из которого задачу заводят. Линейка проекта — список issues репозитория: сколько уже закрыто и сколько ещё осталось. Задачи этот процент не двигают.

## Цель

Приложение для ведения задач в Telegram. Задачи ведут люди в боте. GitHub подключён как интеграция: он показывает, что происходит в репозитории, и не решает за людей, какая задача выполнена.

Бот отвечает на вопрос:

> **Что уже сделано, что делается прямо сейчас, что мешает и какой следующий шаг?**

Разделение ответственности:

- **Telegram** — где живут задачи и где с ними работают;
- **Progress Layer** — доля закрытого бэклога репозитория и что из issues на ком висит;
- **GitHub** — источник этой линейки и картина кода: issues, PR, коммиты, CI.

Бот не создаёт иллюзию точности. Если реальное состояние неизвестно, показывается **«Нет данных»** или **«Требуется подтверждение»**, а не придуманный процент.

## 1. Основной сценарий

Человек открывает свою ветку в группе проекта. Там одно сообщение бота — канвас. Меню в личке нет. Задачу он пишет обычным сообщением в эту же ветку, и она появляется на канвасе.

> **ПРОЕКТ: Общественный сенсор** · 17.09
> **Сделано по проекту:** 42% · осталось 18 из 31
> **Андрей по issues:** закрыл 4 · сейчас на нём 2 · дальше в репозитории 16
>
> **Сделано**
> - #4 архитектура проекта;
> - #8 структура базы данных;
> - #11 Telegram-интерфейс.
>
> **В работе**
> - #40 классификация сигналов — Андрей;
> - #44 AI-интервьюер — Мария.
>
> **Далее**
> - #51 кластеризация похожих сигналов;
> - #56 публичная карточка проблемы.
>
> **Задачи**
> ☐ 7 — Классификация сигнала — 3-й день
> ☑ 9 — Черновик карточки — на подтверждении
>
> **GitHub** `org/sensor`: CI зелёный · открытых PR 2 · milestone Pilot до 12.10

Процент и списки «Сделано / В работе / Далее» — issues репозитория, короткий срез. «Задачи» — то, что человек завёл в этой ветке; у пунктов чекбоксы. Закрытая задача, галочка и смерженный PR процент не двигают. Его двигает смена состояния issue.

## 2. Данные и роли

### 2.1 Проект и репозиторий

Проект — единица людей и учёта. У него имя, описание, таймзона и чат Telegram. По таймзоне проекта считаются «сегодня», границы суток, застой и отчёты.

К проекту можно подключить не больше одного GitHub-репозитория. Один репозиторий можно подключить к нескольким проектам: в одном репозитории работают разные команды. Задачи, роли, списки дня и отчёты у этих проектов отдельные. Зеркало GitHub одно на репозиторий, его читают все проекты, к которым он подключён. Прогресс по issues тоже один на репозиторий: у таких проектов на карточке одна и та же доля.

Проект без репозитория допустим. Задачи, списки дня и блокеры по тишине работают. Процента проекта нет: печатается **«Нет данных»**. Экраны GitHub показывают «репозиторий не подключён».

Репозиторий подключает и сменяет руководитель. Смена репозитория меняет GitHub-картину и линейку прогресса. Задачи и люди остаются. Уже записанные снимки не переписываются.

Milestone — факт GitHub, а не этап задач. На экране GitHub у него название и срок. Отдельного процента у milestone нет: в линейку проекта входят issues всего репозитория, а не одного milestone.

### 2.2 Задача

Задачу создаёт человек сообщением в своей ветке исполнителя. Из issue, PR и коммита задача сама не появляется. Issue, на котором человек стоит assignee, задачей не становится.

Поля: номер внутри проекта, название, описание (можно пустым), проект, приоритет, исполнитель, статус, даты создания, изменения и завершения. Вес в задаче не хранится: он выводится из приоритета. Поля «issue» и «процент задачи» нет.

Статусы:

- `PLANNED` — в плане, в сегодняшний список не стоит;
- `IN_PROGRESS` — стоит в сегодняшнем списке исполнителя;
- `BLOCKED` — два дня в списке без галочки, причина выясняется (см. 2.3);
- `REVIEW` — исполнитель поставил галочку, ждёт подтверждения руководителя;
- `DONE` — руководитель подтвердил;
- `CANCELLED` — делать не будем.

Текст сообщения становится названием. Исполнитель — хозяин ветки. Приоритет по умолчанию `normal`. Задача сразу встаёт на канвас в «Задачи» (`IN_PROGRESS`). Кнопка «в план» переносит её в `PLANNED` на том же канвасе. Исполнителем может быть только `member` или `lead` этого проекта.

Приоритет: `high`, `normal`, `low`. По умолчанию `normal`.

Номер issue или PR, случайно написанный в названии, связью не считается. Бот не разбирает текст задачи в ссылку на GitHub.

Незакрытая задача из списка дня не пропадает: на следующий день она переносится в новый список того же исполнителя, с пометкой, какой день идёт.

Снять задачу может руководитель, либо исполнитель, пока она не `DONE`. Перед удалением участника из проекта его незакрытые задачи передают другому исполнителю или снимают: задачи без участника проекта не остаётся.

### 2.3 Блокеры и застой

Задача в `IN_PROGRESS`, которую не отметили галочкой два дня, переходит в `BLOCKED`. Бот пишет в ветку исполнителя: «7 не двигается 3-й день, что мешает?» — с кнопкой «нет блокера». Текст ответа становится причиной. Кнопка «нет блокера» возвращает задачу в `IN_PROGRESS`. По одной задаче бот спрашивает не чаще раза в два дня.

`PLANNED` так не блокируется: план не обязан двигаться каждый день. `REVIEW` застоем исполнителя не считается: галочка уже стоит. Если руководитель не подтверждает и не возвращает задачу дольше двух дней, бот один раз за два дня напоминает руководителям проекта.

Поля блокера задачи:

- **причина** — ответ исполнителя; пока его нет, строка не печатается;
- **что требуется** — необязательно, иначе строка не печатается.

«Влияние» по графу issues не считается: у задачи нет issue, от которого можно было бы вывести, кто кого ждёт.

Отдельно от задач бот показывает факты застоя репозитория. Они не переводят задачу в `BLOCKED` и не ссылаются на номер задачи:

- CI основной ветки красный — строка на каждом проекте этого репозитория;
- открытый PR без движения дольше двух дней, и его автор или запрошенный ревьюер — участник проекта;
- у такого PR красный CI — это та же строка, с пометкой про CI.

Issue без коммитов, без PR и без свежих комментариев в этот список не входит. На экране GitHub он виден только числом: сколько открытых issues не обновлялись дольше двух дней.

Один порог на всё: два дня. И на галочку задачи, и на PR, и на напоминание руководителю.

### 2.4 Участники и доступ

Участник — аккаунт Telegram. К нему можно записать логин GitHub. Логин нужен, чтобы коммиты, PR и закрытые issues этого человека узнавались на канвасе. Без логина участник ведёт задачи как обычно, а его действия в GitHub остаются на экране репозитория под именем логина и к человеку в боте не приклеиваются.

Один логин GitHub принадлежит одному пользователю бота. В поле хранится текущий логин: старый логин после смены ника новые факты уже не сопоставит.

Один человек может состоять в нескольких проектах. Роль задаётся в каждом проекте отдельно.

Роли в MVP две:

- `member` — исполнитель, своя ветка (topic) для списка дня;
- `lead` — руководитель: подтверждает завершение, заводит проект, подключает репозиторий, собирает участников.

Роли «только просмотр» в MVP нет. Кого добавили в проект, тот ведёт задачи.

Первый, кто нажал `/start`, — корень бота. Он первый `lead` и единственный, кто появляется сам. В каждом проекте, который он заводит, он `lead`. Остальные пользователи боту известны только после своего `/start` и ничего не могут, пока корень или `lead` проекта не добавит их. Второй `/start` корнем не становится.

Бот отвечает корню и участникам проекта. Остальным — отказ, без раскрытия данных.

Галочку ставит исполнитель. Снять галочку до подтверждения может он же: задача возвращается в `IN_PROGRESS` и снова стоит в сегодняшнем списке. Руководитель из `REVIEW` либо подтверждает `DONE`, либо возвращает задачу в работу. Если в проекте один руководитель и он же исполнитель, он подтверждает свою задачу сам. Если руководителей несколько, свою задачу подтверждает другой руководитель.

## 3. GitHub-интеграция

Бот читает репозиторий: issues, pull requests, коммиты, статусы CI, milestones, релизы, даты и логины авторов. Ветки и метки сами по себе на экраны не выводятся.

Доступ — через **GitHub App**, не через личный токен: приватные репозитории, секрет для webhooks, отдельные лимиты.

Обновление — webhooks (`push`, `pull_request`, `issues`, `workflow_run`, `release`). Опрос только догоняет пропущенную доставку.

**Синхронизация односторонняя:** GitHub → бот. Issues, PR, assignees, метки и комментарии меняет человек в GitHub. Бот туда не пишет.

Зеркало хранится на репозитории. Проект его не копирует себе. Два проекта с одним репозиторием видят одни и те же объекты GitHub; различается только то, какие из них относятся к участникам данного проекта (см. 3.2).

### 3.1 Что видно из зеркала

На канвасе, если репозиторий подключён, — одна строка: состояние CI основной ветки, число открытых PR, ближайший открытый milestone с датой. Процента у milestone нет. Нет даты — строка milestone не печатается. CI неизвестен — на этой строке «Нет данных», и это не блокер. Отдельного экрана GitHub нет.

В зеркале для этой строки, для блокеров и для отчёта лежат:

- CI основной ветки;
- до пяти открытых PR: номер, название, автор, возраст, CI; сначала те, где автор или ревьюер — участник проекта;
- до пяти последних коммитов: автор и сообщение;
- открытые issues числом, среди них — сколько не обновлялись дольше двух дней, и до пяти последних по дате обновления; отдельно, сколько открытых issues назначено на участников проекта (см. 3.4);
- открытые milestones: название и срок;
- последний релиз, если он есть;
- если репозиторий подключён ещё к другим проектам — их имена, чтобы одинаковая GitHub-картина не выглядела ошибкой.

Полный список из десятков issues бот в чат не вываливает.

Связи `blocked by` и sub-issues хранятся в зеркале и дописываются к issue, который и так попал в срез канваса. Очередь плана от них не зависит.

### 3.2 Чьи это факты

Факт GitHub попадает на проект по двум правилам.

**Общие для репозитория.** Красный CI основной ветки виден каждому проекту, к которому подключён этот репозиторий. Зелёный CI отдельной строкой в блокеры не пишется.

**Личные.** Коммит, PR и закрытый issue относятся к участнику, если логин автора совпал с `github_login`. Для PR учитываются автор и запрошенный ревьюер, для коммита — автор, для закрытого issue — кто его закрыл. Такой факт виден проектам, где этот человек участник и куда подключён этот репозиторий.

Логин, который не совпал ни с одним участником проектов этого репозитория, остаётся на экране GitHub под своим именем и в блокеры проектов не поднимается. Иначе чужой PR стал бы блокером обеих команд.

Один и тот же PR не дублируется внутри одного проекта, даже если и автор, и ревьюер состоят в нём. В двух проектах, где состоит один и тот же автор, строка будет в обоих: человек участвует в обоих.

### 3.3 Расхождение учёта

Прогресс проекта считается по issues. Задачи — другой слой: день, галочка, подтверждение. Работа, которую не завели задачей, на канвас в блок «Задачи» не попадает. Это нормальная граница, а не дыра, которую надо закрыть импортом issues в задачи.

Сигнал расхождения — проектный, за календарные сутки по таймзоне проекта. Он загорается, когда одновременно:

- в репозитории есть коммит, смерженный PR или закрытый issue, и логин действующего лица совпал с участником **этого** проекта;
- в проекте за те же сутки не создана ни одна задача и ни одна не перешла в `DONE`.

Текст: «В репозитории есть движение, в задачах за сутки тишина».

Сигнал не меняет статусы и не создаёт блокер. Движение чужой команды в том же репозитории этот проект не тревожит. Красный CI расхождением не считается: это не сделанная работа, а сломанная проверка.

### 3.4 Где человек стоит в бэклоге

Да. Место человека в проекте читается по issues, а не по задачам бота.

Issue относится к пользователю, если среди его assignees есть `github_login` этого пользователя. Логин сопоставляется с аккаунтом Telegram в момент показа. Задача из этого не создаётся, статус задачи не меняется, процент проекта не делится по людям.

- **Прошёл** — такие issues закрыты как сделанные (`completed`).
- **Сейчас** — такие issues ещё открыты. Это и есть «где он сейчас» в бэклоге.
- **Дальше** — остальные открытые issues того же репозитория: они ещё не на нём.

Без логина этого среза нет: строка человека печатается как «нет сопоставления с GitHub». Задачи при этом работают.

Один issue с несколькими assignees входит в «сейчас» каждого совпавшего участника и в процент проекта — один раз. Чужой логин, не записанный ни на кого в боте, на карточке человека не появляется.

## 4. Расчёт прогресса

Линейка — репозиторий проекта, не набор задач, которые люди завели по ходу дня. В GitHub бэклог расписан целиком, в боте задач мало, и они закрываются почти сразу. Процент по задачам поэтому почти всегда высокий и почти только растёт. Процент по issues ведёт себя иначе: полный бэклог с самого начала стоит в знаменателе, новая незакрытая работа процент снижает.

`прогресс = issues completed / (открытые + completed)`

Каждый issue весит одинаково. Размер работы внутри issue бот не оценивает. Поэтому рядом с процентом всегда печатается остаток: **осталось 18 из 31**. Высокие 90% без остатка прячут хвост бэклога, остаток его показывает.

В числителе только `completed`. Открытый issue стоит в знаменателе, кем бы он ни был назначен. Issue, закрытый как `not_planned`, не стоит ни там, ни там: снятая работа не раздувает процент. Смерженный PR и закрытая задача бота в формулу не входят.

Если репозиторий не подключён или в формуле пустой знаменатель, процента нет: печатается **«Нет данных»**, не 0%.

У двух проектов с одним репозиторием процент совпадает: бэклог общий. Делёж issues одного репозитория по проектам в эту формулу не входит.

Общий процент в личном отчёте считается той же формулой по issues репозиториев этих проектов, каждый репозиторий один раз. Проект без репозитория в общую цифру не входит. Это доля закрытого бэклога, а не среднее арифметическое карточек. В групповой отчёт одного проекта строка «все проекты» не подставляется.

Снимок пишется раз в сутки по таймзоне проекта и хранит эту долю. Из снимков строится динамика. Пропуски не заполняются соседними числами. Смена репозитория старые снимки не переписывает.

## 5. Канвас

Канвас — то самое сообщение из раздела 1. Оно живёт в ветке исполнителя. Личка бота этого экрана не дублирует и меню не показывает. Бот правит одно сообщение, второе на те же сутки не создаёт. Как задача на него попадает — в разделе 6.

Состав, сверху вниз:

- дата и имя проекта;
- доля бэклога и остаток открытых issues (раздел 4);
- строка этого человека по 3.4;
- **Сделано** — до пяти последних issues `completed`;
- **В работе** — до пяти открытых issues, у которых есть assignee;
- **Далее** — до пяти открытых issues без assignee;
- **Задачи** — чекбоксы его `IN_PROGRESS`, `BLOCKED` и `REVIEW`. Номера issue и PR на строке задачи нет;
- **План** — его `PLANNED`. Сначала больший приоритет, внутри одного приоритета раньше созданная выше. Пустой план не печатается;
- **Блокеры** — причины его задач в `BLOCKED` и его строки CI / PR из 2.3. Чужой PR сюда не входит. Красный CI основной ветки — отдельная строка;
- **GitHub** — одна строка из 3.1, либо «репозиторий не подключён»;
- **Динамика** — последние снимки доли одной строкой: `10.09 — 31% · 17.09 — 42%`.

Если за сутки сработало расхождение из 3.3, его строка стоит под GitHub.

Подтверждённая задача с канваса уходит. В блоке «Задачи» она больше не висит. Дата подтверждения остаётся в отчёте, не отдельным экраном.

### 5.8 Настройки

Имя проекта, описание, таймзона, чат, участники и роли, ветка списка дня, топик отчётов, логин GitHub, подключённый репозиторий, время группового отчёта. Как это проходит в первый раз — в 5.9.

Смена таймзоны не переписывает уже отправленный канвас. Новые сутки и новый застой считаются по новой зоне.

### 5.9 Онбординг

#### Первый пользователь

Пока в боте никого нет, первый `/start` создаёт корня. Бот пишет, что он руководитель и может завести проект. Позже `/start` только запоминает аккаунт Telegram и говорит, что доступ появится, когда руководителя добавят в проект.

#### Новый проект

Проект заводит корень или `lead`. Делает это в личке бота.

1. «Новый проект»: имя, описание, таймзона.
2. Бот просит супергруппу с темами и права администратора: сообщения и управление темами.
3. Когда бота добавили, руководитель подтверждает, что этот чат — чат проекта. До подтверждения канвас и отчёты некуда отправлять.
4. Репозиторий — отдельный шаг, его можно пропустить. Бот показывает репозитории установки GitHub App. Подключает и меняет только руководитель.
5. Бот создаёт в группе топик «Отчёты» и записывает его топиком отчётов. Затем спрашивает время ежедневной отправки. Пока время не названо, расписание выключено. Команда `/report` в группе уже отвечает.

#### Участник

1. Человек входит в группу проекта.
2. Открывает бота в личке и отправляет `/start`. Бот запоминает аккаунт Telegram.
3. Корень или `lead` проекта видит людей, которые уже нажали `/start` и ещё не в проекте, и добавляет их как `member`.
4. Бот спрашивает у человека логин GitHub. Шаг можно пропустить и заполнить позже. Логин один на пользователя бота, не на каждый проект.
5. Бот сначала спрашивает, есть ли у человека топик в группе. Если есть — руководитель указывает его, бот ставит туда канвас. Если нет — бот создаёт топик с именем человека и ставит канвас туда. В топик пишет, что задача — это сообщение в этом топике.

Пока групповой чат не привязан, топик списка дня пуст: список появится после привязки.

#### Первое сообщение сотруднику

Одним текстом в личку и тем же текстом в его топик:

- где его ветка и канвас;
- задача — сообщение в этой ветке, она появляется на канвасе;
- галочка отправляет задачу руководителю и процент проекта не меняет;
- место в бэклоге — issues, где он assignee; без логина GitHub этой строки нет.

## 6. Как задача попадает на канвас

Нативный чеклист Telegram боту недоступен: `sendChecklist` требует Business-аккаунт и не работает в ветках супергруппы. Канвас — сообщение, которое бот редактирует. Чекбоксы только у задач, инлайн-кнопками. Issues, PR и CI кнопками не закрываются.

Канвас свой у каждого исполнителя: пара «проект + исполнитель + дата» — не больше одного сообщения. Дата — по таймзоне проекта. Ветка есть и у `member`, и у `lead`.

Человек пишет в свою ветку обычный текст. Бот заводит задачу и дописывает её чекбоксом в блок «Задачи» того же канваса. Чужие ветки задачу ему не создают. Шага «выберите issue» нет.

- канваса на сегодня нет — новое сообщение;
- уже есть — правка того же сообщения;
- текст не помещается в лимит Telegram — сначала ужимаются срезы issues, блокеры и динамика. Задачи не выкидываются. Если не влезают уже они, бот отказывает: канвас заполнен. Второе сообщение на ту же дату не создаётся.

Незакрытые задачи (`IN_PROGRESS`, `BLOCKED`) на следующий день переносятся на новый канвас, с пометкой, какой это день. `REVIEW` назавтра остаётся на канвасе отмеченной, пока руководитель не ответит. `PLANNED` переносится в блок «План» без чекбокса.

Галочка переводит задачу в `REVIEW`. `DONE` ставит руководитель по правилу из 2.4, кнопкой на этом же канвасе. Пока он не ответил, процент проекта прежний.

Передача исполнителя убирает пункт с канваса прежнего и ставит на канвас нового, если задача была `IN_PROGRESS` или `BLOCKED`.

## 7. Отчёты

### 7.1 Ежедневный

В личку отчёт начинается с общего прогресса по репозиториям этого пользователя, дальше блок на каждый его проект. Доля в блоке проекта — из раздела 4. GitHub вынесен вниз, по одному блоку на репозиторий, даже если репозиторием пользуются два проекта.

> ## DAILY DEVELOPMENT REPORT
> **Все проекты:** 37% → 39%
>
> ### Общественный сенсор
> **Прогресс:** 42% → 45%
>
> **За день:** ✅ подтверждено 3 · 🆕 создано 2 · ⚠️ заблокировано 1
>
> **Сейчас:** 7 — Классификация сигнала
> **Риск:** нет стабильного доступа к одному из источников данных
> **Следующий шаг:** подключить резервный источник
>
> ### GitHub `org/sensor`
> CI зелёный · смержено PR 1 · коммитов 6
> Проекты: Общественный сенсор

«В репозитории есть движение, в задачах за сутки тишина» печатается в блоке того проекта, для которого условие из 3.3 выполнено.

В групповую ветку уходит отчёт только её проекта, без строки «все проекты». Блок репозитория в группе есть: это репозиторий данного проекта.

### 7.2 Еженедельный

> ## WEEKLY DEVELOPMENT REPORT
> **Все проекты:** было 24% → стало 37%
>
> ### Общественный сенсор
> **Прогресс:** было 28% → стало 42%
>
> **Сделано:** подтверждённые за неделю задачи
> **Что замедлило разработку:** причины блокеров и строки застоя PR / CI
> **Следующая неделя:** ближайшие задачи плана
>
> ### GitHub `org/sensor`
> commits 47 · PR смержено 8 · issues закрыто 13

Числа GitHub — про репозиторий за неделю, один раз. В сумму по проектам они не входят.

### 7.3 Откуда берутся текстовые блоки

Их никто не пишет вручную.

- **Сейчас** и **Следующий шаг** — по правилам 5.1.
- **Риск** и **Что замедлило разработку** — причины блокеров задач и факты из 2.3, дословно: «PR #138 без движения 4 дня, CI красный».
- **За день** — названия задач, которые за сутки созданы или перешли в `DONE`. Это задачи, не сообщения коммитов.
- Блок **GitHub** — смерженные PR, коммиты и закрытые issues репозитория. Внутрь абзаца про задачи эти названия не подмешиваются.

Нет данных — блок не печатается. Пустой процент не заменяется нулём.

### 7.4 Доставка

Отчёт читают в двух местах.

- **В личке бота** — `/report` в любой момент. Карточки проектов пользователя и блоки их репозиториев, со строкой «все проекты».
- **В командном топике группы** — по расписанию, и по `/report`, если команду написали в групповом чате этого проекта. Ответ ставится в топик отчётов: отчёт только этого проекта, без строки «все проекты».

Топик отчётов может не совпадать с топиками списков дня и хранится отдельно. На проект настраиваются время и включение групповой отправки. Личный `/report` работает и при выключенной рассылке. Пока топик отчётов не задан, групповой `/report` отвечает в том чате, откуда его вызвали. Недельный отчёт, когда он есть, идёт тем же разделением: личка и топик отчётов.

## 8. Архитектура

```
Telegram Bot → Bot API / Webhook → Backend → Progress Engine → PostgreSQL
                                             ├── Tasks
                                             ├── GitHub mirror (на репозиторий)
                                             ├── Event Processor
                                             └── Report Generator
GitHub: API + Webhooks → Event Processor
```

Задачи с зеркалом не соединены внешним ключом. Сопоставление человека и логина происходит в момент показа.

---

## 9. Структура данных

### repositories

`id`, `owner`, `name`, `default_branch_ci`

### projects

`id`, `name`, `description`, `repository_id` (пусто — репозиторий не подключён), `timezone`, `telegram_chat_id`, `created_at`

Один `repository_id` может стоять у нескольких проектов.

### users

`id`, `telegram_user_id`, `github_login` (пусто — сопоставления нет), `name`

Оба внешних ключа уникальны. Пустой логин уникальности не нарушает.

### project_members

`id`, `project_id`, `user_id`, `role` (`member` / `lead`), `topic_id` — ветка списка дня; пусто, пока чат проекта не привязан

### tasks

`id`, `project_id`, `number`, `title`, `description`, `status`, `priority` (`high` / `normal` / `low`), `assignee_id`, `created_at`, `updated_at`, `completed_at`

`number` уникален в проекте. Колонок issue и прогресса задачи нет. Вес не хранится.

### milestones

`id`, `repository_id`, `milestone_number`, `title`, `state`, `due_on` — зеркало GitHub, не этапы проекта

### issues

`id`, `repository_id`, `issue_number`, `title`, `state`, `state_reason` (`completed` / `not_planned`, пусто у открытого), `closed_by_login`, `updated_at`, `closed_at`

Природный ключ — репозиторий и номер, не проект.

### issue_assignees

`issue_id`, `login` — зеркало assignees. Один issue может быть назначен нескольким людям. По этим логинам строится срез 3.4.

### issue_dependencies

`issue_id`, `depends_on_issue_id`, `link_type` (`blocked_by` / `sub_issue`) — зеркало для строки на экране GitHub

### pull_requests

`id`, `repository_id`, `pull_request_number`, `title`, `author_login`, `state`, `ci_status`, `updated_at`, `merged_at`, `merged_by_login`

### commits

`id`, `repository_id`, `sha`, `message`, `author_login`, `created_at` — хвост для экрана и блока отчёта, не журнал всей истории

### blockers

`id`, `task_id`, `reason`, `required_action`, `asked_at`, `resolved_at`

Только блокеры задач. Строки про CI и PR в эту таблицу не пишутся: они выводятся из зеркала.

### task_lists

`id`, `project_id`, `assignee_id`, `topic_id`, `message_id`, `list_date`

Уникально `project_id + assignee_id + list_date`.

### task_list_items

`id`, `list_id`, `task_id`, `position`, `is_done`, `carried_from_list_id`

### report_targets

`id`, `project_id`, `chat_id`, `topic_id`, `report_type` (`daily` / `weekly`), `schedule_cron`, `timezone` (если не задана — из проекта), `is_enabled`

### events

`id`, `source`, `event_type`, `payload`, `created_at` — журнал только дополняется

### progress_snapshots

`id`, `project_id`, `progress`, `created_at`

## 10. AI-слой

AI может пересказать уже собранные блоки отчёта обычным языком и заметить расхождение из 3.3 теми же фактами.

AI не является источником истины. Он не заводит задачи, не ставит `DONE`, не придумывает связь задачи с issue и не добавляет фактов, которых нет в задачах и в зеркале.

---

## 11. Definition of Done

Задача проекта выполнена, когда руководитель подтвердил её по правилу из 2.4 и у неё нет открытого блокера.

Смерженный PR, закрытый issue и зелёный CI таким подтверждением не являются.

---

## 12. Объём работ

### MVP

1. Канвас в ветке исполнителя; несколько проектов на одном репозитории; проект может быть без репозитория. Меню в личке нет.
2. Участники, роли, доступ по составу проекта, логин GitHub у человека.
3. Задачи со статусами и приоритетом, без связи с issue.
4. Прогресс проекта — доля `completed` issues репозитория и остаток открытых. Задачи и галочка этот процент не двигают. Место человека в бэклоге — по assignees и `github_login`.
5. На канвасе: доля бэклога, срез issues, задачи с чекбоксами, план, блокеры, строка GitHub, короткая динамика.
6. Блокировка задачи через два дня и вопрос исполнителю; отдельно — CI и застоявшиеся PR участников.
7. Задача создаётся сообщением в ветке исполнителя и попадает на канвас. Незакрытое переносится на следующий день.
8. Ежедневный отчёт в личке бота и в топике отчётов группы: по команде `/report` и по расписанию в топик. GitHub — блоком на репозиторий.
9. Онбординг: новый проект, привязка чата и репозитория, добавление участника, логин GitHub, ветка исполнителя с канвасом и топик отчётов.
10. Webhooks GitHub App как основной канал, опрос — только сверка пропущенного.
11. Строка расхождения «в репозитории есть движение, в задачах тишина».

Не входит в MVP: связь задачи с issue или PR, заведение задач из issues, роль просмотра без своих задач, делёж issues одного репозитория по проектам, несколько репозиториев у одного проекта, зависимости между задачами, отдельный процент milestone, смена объектов GitHub, AI, недельный отчёт, динамика, публичный dashboard.

### Дальше

AI-пересказ блоков отчёта, недельные отчёты, динамика по снимкам, несколько репозиториев у одного проекта.

Публичный dashboard, история проекта, визуальная шкала времени, прогнозирование сроков — только как вспомогательная аналитика, без неподтверждённой точности.

## 13. Критерий успеха

> Насколько быстро человек понимает состояние разработки, не открывая GitHub и не спрашивая разработчиков.

Целевое поведение: **открыл свою ветку → за 10–20 секунд по канвасу понял, какая доля проекта уже сделана и сколько issues осталось, где в бэклоге стоит человек, какие задачи на нём сегодня и что блокирует работу.** Картина репозитория — одна строка рядом. Задачи остаются учётом дня и процент проекта не подменяют.
