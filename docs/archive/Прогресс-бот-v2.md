# Прогресс-бот — редакция 2

Редакция 1 — [`Прогресс-бот.md`](Прогресс-бот.md). Там каждая задача обязана ссылаться на issue, и из этого issue берутся этап, исполнитель по умолчанию, порядок плана, сигнал «похоже, готово», застой и список issues без задач.

Редакция 2 этот стык убирает. Задача — шаг, который человек ведёт в Telegram. GitHub — зеркало репозитория: issues, PR, коммиты, CI, milestones. Общее между ними два: человек (аккаунт Telegram и логин GitHub) и проект (к нему подключён репозиторий). Issue не является родителем задачи, каталогом при создании и ключом прогресса.

## Цель

Приложение для ведения задач в Telegram. Задачи ведут люди в боте. GitHub подключён как интеграция: он показывает, что происходит в репозитории, и не решает за людей, какая задача выполнена.

Бот отвечает на вопрос:

> **Что уже сделано, что делается прямо сейчас, что мешает и какой следующий шаг?**

Разделение ответственности:

- **Telegram** — где живут задачи и где с ними работают;
- **Progress Layer** — что задачи означают для проекта: прогресс, блокеры, следующий шаг;
- **GitHub** — что изменилось в коде репозитория.

Бот не создаёт иллюзию точности. Если реальное состояние неизвестно, показывается **«Нет данных»** или **«Требуется подтверждение»**, а не придуманный процент.

---

## 1. Основной сценарий

Пользователь открывает бота и видит карточку на каждый свой проект: прогресс по задачам, что сделано, что в работе, что в плане, что мешает, ближайший следующий шаг и короткую сводку репозитория, если он подключён.

> **ПРОЕКТ: Общественный сенсор**
> **Сделано по задачам:** 42%
> **Сейчас:** 7 — Классификация сигнала — Андрей, 3-й день
>
> **Сделано**
> - архитектура проекта;
> - структура базы данных;
> - Telegram-интерфейс.
>
> **В работе**
> - классификация сигналов;
> - AI-интервьюер.
>
> **Далее**
> - кластеризация похожих сигналов;
> - публичная карточка проблемы.
>
> **GitHub** `org/sensor`: CI зелёный · открытых PR 2 · milestone Pilot до 12.10

Процент на карточке — только из задач бота. Закрытый issue и смерженный PR сами по себе процент не двигают.

## 2. Данные и роли

### 2.1 Проект и репозиторий

Проект — единица людей и учёта. У него имя, описание, таймзона и чат Telegram. По таймзоне проекта считаются «сегодня», границы суток, застой и отчёты.

К проекту можно подключить не больше одного GitHub-репозитория. Один репозиторий можно подключить к нескольким проектам: в одном репозитории работают разные команды. Задачи, роли, списки дня, прогресс и отчёты у этих проектов отдельные. Зеркало GitHub одно на репозиторий, его читают все проекты, к которым он подключён.

Проект без репозитория допустим. Задачи, списки дня, блокеры по тишине и прогресс работают. Экраны GitHub показывают «репозиторий не подключён».

Репозиторий подключает и сменяет руководитель. Смена репозитория меняет GitHub-картину проекта. Задачи, люди и уже посчитанный прогресс остаются.

Milestone — факт GitHub, а не этап задач. На экране GitHub у него название и срок. Процента у milestone нет: закрытые issues внутри него не являются прогрессом проекта, и задачи по milestone не раскладываются.

### 2.2 Задача

Задачу создаёт и ведёт человек в боте. Из issue, PR и коммита задача сама не появляется.

Поля: номер внутри проекта, название, описание (можно пустым), проект, приоритет, исполнитель, статус, даты создания, изменения и завершения. Вес в задаче не хранится: он выводится из приоритета. Поля «issue» и «процент задачи» нет.

Статусы:

- `PLANNED` — в плане, в сегодняшний список не стоит;
- `IN_PROGRESS` — стоит в сегодняшнем списке исполнителя;
- `BLOCKED` — два дня в списке без галочки, причина выясняется (см. 2.3);
- `REVIEW` — исполнитель поставил галочку, ждёт подтверждения руководителя;
- `DONE` — руководитель подтвердил;
- `CANCELLED` — делать не будем.

При создании автор пишет формулировку, выбирает исполнителя и приоритет и решает, куда положить задачу: в сегодняшний список (`IN_PROGRESS`) или в план (`PLANNED`). Исполнитель по умолчанию — сам автор. Исполнителем может быть только `member` или `lead` этого проекта. Без исполнителя задача не создаётся.

Приоритет: `high`, `normal`, `low`. По умолчанию `normal`.

Номер issue или PR, случайно написанный в названии, связью не считается. Бот не разбирает текст задачи в ссылку на GitHub.

Незакрытая задача из списка дня не пропадает: на следующий день она переносится в новый список того же исполнителя, с пометкой, какой день идёт.

Снять задачу может руководитель, либо исполнитель, пока она не `DONE`. Перед удалением участника из проекта его незакрытые задачи передают другому исполнителю или снимают: задачи без участника проекта не остаётся.

### 2.3 Блокеры и застой

Задача в `IN_PROGRESS`, которую не отметили галочкой два дня, переходит в `BLOCKED`. Бот пишет исполнителю в личку: «7 не двигается 3-й день, что мешает?» — с кнопкой «нет блокера». Текст ответа становится причиной. Кнопка «нет блокера» возвращает задачу в `IN_PROGRESS`. По одной задаче бот спрашивает не чаще раза в два дня.

`PLANNED` так не блокируется: план не обязан двигаться каждый день. `REVIEW` застоем исполнителя не считается: галочка уже стоит. Если руководитель не подтверждает и не возвращает задачу дольше двух дней, бот один раз за два дня напоминает руководителям проекта.

Поля блокера задачи:

- **причина** — ответ исполнителя; пока его нет, строка не печатается;
- **что требуется** — необязательно, иначе строка не печатается.

«Влияние» по графу issues не считается: у задачи нет issue, от которого можно было бы вывести, кто кого ждёт.

Отдельно от задач бот показывает факты застоя репозитория. Они не переводят задачу в `BLOCKED` и не ссылаются на номер задачи:

- CI основной ветки красный — строка на каждом проекте этого репозитория;
- открытый PR без движения дольше двух дней, и его автор или запрошенный ревьюер — участник проекта;
- у такого PR красный CI — это та же строка, с пометкой про CI.

Issue без коммитов, без PR и без свежих комментариев в этот список не входит. На экране GitHub он виден только числом: сколько открытых issues не обновлялись дольше двух дней.

Один порог на всё: два дня. И на галочку задачи, и на PR, и на напоминание руководителю.

### 2.4 Участники и доступ

Участник — аккаунт Telegram. К нему можно записать логин GitHub. Логин нужен, чтобы коммиты, PR и закрытые issues этого человека узнавались на экранах. Без логина участник ведёт задачи как обычно, а его действия в GitHub остаются на экране репозитория под именем логина и к человеку в боте не приклеиваются.

Один логин GitHub принадлежит одному пользователю бота. В поле хранится текущий логин: старый логин после смены ника новые факты уже не сопоставит.

Один человек может состоять в нескольких проектах. Роль задаётся в каждом проекте отдельно.

Роли:

- `viewer` — только просмотр, своей ветки задач нет;
- `member` — исполнитель, своя ветка (topic) для списка дня;
- `lead` — руководитель: подтверждает завершение, подключает репозиторий, собирает участников.

Бот отвечает только участникам проекта. Остальным — отказ, без раскрытия данных.

Галочку ставит исполнитель. Снять галочку до подтверждения может он же: задача возвращается в `IN_PROGRESS` и снова стоит в сегодняшнем списке. Руководитель из `REVIEW` либо подтверждает `DONE`, либо возвращает задачу в работу. Если в проекте один руководитель и он же исполнитель, он подтверждает свою задачу сам. Если руководителей несколько, свою задачу подтверждает другой руководитель.

## 3. GitHub-интеграция

Бот читает репозиторий: issues, pull requests, коммиты, статусы CI, milestones, релизы, даты и логины авторов. Ветки и метки сами по себе на экраны не выводятся.

Доступ — через **GitHub App**, не через личный токен: приватные репозитории, секрет для webhooks, отдельные лимиты.

Обновление — webhooks (`push`, `pull_request`, `issues`, `workflow_run`, `release`). Опрос только догоняет пропущенную доставку.

**Синхронизация односторонняя:** GitHub → бот. Issues, PR, assignees, метки и комментарии меняет человек в GitHub. Бот туда не пишет.

Зеркало хранится на репозитории. Проект его не копирует себе. Два проекта с одним репозиторием видят одни и те же объекты GitHub; различается только то, какие из них относятся к участникам данного проекта (см. 3.2).

### 3.1 Что видно из зеркала

На карточке проекта, если репозиторий подключён, — одна строка: состояние CI основной ветки, число открытых PR, ближайший открытый milestone с датой. Процента у milestone нет. Нет даты — строка milestone не печатается. CI неизвестен — на этой строке «Нет данных», и это не блокер.

Экран «GitHub» показывает картину репозитория, а не каталог для заведения задач:

- CI основной ветки;
- до пяти открытых PR: номер, название, автор, возраст, CI; сначала те, где автор или ревьюер — участник проекта;
- до пяти последних коммитов: автор и сообщение;
- открытые issues числом, среди них — сколько не обновлялись дольше двух дней, и до пяти последних по дате обновления; отдельно число issues, где assignee — участник проекта;
- открытые milestones: название и срок;
- последний релиз, если он есть;
- если репозиторий подключён ещё к другим проектам — их имена, чтобы одинаковая GitHub-картина не выглядела ошибкой.

Полный список из десятков issues бот в чат не вываливает.

Связи `blocked by` и sub-issues хранятся в зеркале и показываются строкой у того issue, который и так попал на экран. Очередь плана от них не зависит.

### 3.2 Чьи это факты

Факт GitHub попадает на проект по двум правилам.

**Общие для репозитория.** Красный CI основной ветки виден каждому проекту, к которому подключён этот репозиторий. Зелёный CI отдельной строкой в блокеры не пишется.

**Личные.** Коммит, PR и закрытый issue относятся к участнику, если логин автора совпал с `github_login`. Для PR учитываются автор и запрошенный ревьюер, для коммита — автор, для закрытого issue — кто его закрыл. Такой факт виден проектам, где этот человек участник и куда подключён этот репозиторий.

Логин, который не совпал ни с одним участником проектов этого репозитория, остаётся на экране GitHub под своим именем и в блокеры проектов не поднимается. Иначе чужой PR стал бы блокером обеих команд.

Один и тот же PR не дублируется внутри одного проекта, даже если и автор, и ревьюер состоят в нём. В двух проектах, где состоит один и тот же автор, строка будет в обоих: человек участвует в обоих.

### 3.3 Расхождение учёта

Прогресс считается только по заведённым задачам. Работа, которую в бот не занесли, в процент не входит. Это нормальная граница, а не дыра, которую надо закрыть импортом issues.

Сигнал расхождения — проектный, за календарные сутки по таймзоне проекта. Он загорается, когда одновременно:

- в репозитории есть коммит, смерженный PR или закрытый issue, и логин действующего лица совпал с участником **этого** проекта;
- в проекте за те же сутки не создана ни одна задача и ни одна не перешла в `DONE`.

Текст: «В репозитории есть движение, в задачах за сутки тишина».

Сигнал не меняет статусы и не создаёт блокер. Движение чужой команды в том же репозитории этот проект не тревожит. Красный CI расхождением не считается: это не сделанная работа, а сломанная проверка.

## 4. Расчёт прогресса

Прогресс проекта:

`прогресс = вес задач в DONE / вес задач проекта, кроме CANCELLED`

Вес из приоритета: `high` — 3, `normal` — 2, `low` — 1. Пока все задачи остались `normal`, формула совпадает с «подтверждённые / все незакрытые отменой».

В числителе только `DONE`. Галочка (`REVIEW`) процент не двигает. `PLANNED`, `IN_PROGRESS`, `BLOCKED` и `REVIEW` стоят в знаменателе. `CANCELLED` не стоит ни там, ни там: снятая работа не раздувает процент.

Если знаменатель пуст, процента нет: печатается **«Нет данных»**, не 0%.

Общий процент нескольких проектов считается той же формулой по их задачам вместе. Шкала веса одна, поэтому складывать можно. Это доля закрытой учтённой работы, а не «насколько каждый проект близок к цели». В отчёте в личку эта строка идёт рядом с проектными. В групповой отчёт одного проекта она не подставляется.

Снимок прогресса пишется раз в сутки по таймзоне проекта. Из снимков строится динамика. Пропуски не заполняются соседними числами.

## 5. Telegram-интерфейс

Проект в меню не выбирают. Каждый экран показывает карточку на проект, в котором состоит пользователь: сверху те, где задачи менялись позже. Один проект — одна карточка. Проценты карточек между собой не складываются. Общая цифра есть только в личном отчёте.

Главное меню: **📊 ПРОГРЕСС**, **🔨 В РАБОТЕ**, **✅ СДЕЛАНО**, **📋 ПЛАН**, **🐙 GITHUB**, **⚠️ БЛОКЕРЫ**, **📈 ДИНАМИКА**, **⚙️ НАСТРОЙКИ**.

### 5.1 Прогресс

Процент, числа по статусам (подтверждено, в работе, заблокировано, на подтверждении, в плане), «Последнее изменение», «Сейчас», «Следующий шаг».

- **Сейчас** — задача в `IN_PROGRESS` с самым свежим изменением; при равенстве — с большим весом. Нет таких задач — строка не печатается.
- **Следующий шаг** — первая задача плана. Нет плана — строка не печатается.
- Ниже — строка GitHub из 3.1, либо «репозиторий не подключён».
- Если за сутки сработало расхождение из 3.3 — его строка на карточке.

### 5.2 В работе

Задачи в сегодняшних списках проекта:

> **7 — Классификация сигнала** — Андрей, 3-й день

Номера issue и PR на строке задачи нет.

### 5.3 Сделано

Подтверждённые задачи с датой подтверждения:

> ✅ **Архитектура БД** — подтверждено 17.09.2026

### 5.4 План

Задачи в `PLANNED`. Сначала больший приоритет. Внутри одного приоритета раньше созданная стоит выше: она дольше ждёт.

### 5.5 Блокеры

Два разных списка.

Задачи в `BLOCKED`:

> ⚠️ **12 — Поиск подтверждений** — Андрей
> Причина: нет стабильного доступа к одному из источников данных.
> Что требуется: выбрать альтернативный источник.

Факты репозитория из 2.3, без привязки к задаче:

> ⏳ **PR #138** без движения 4 дня, CI красный. Автор: Андрей

Красный CI основной ветки — отдельная строка, если он красный. Чужие PR, автор которых не участник проекта, здесь не появляются.

### 5.6 GitHub

Техническая картина репозитория из 3.1. Это не список «выберите issue». Задачу с этого экрана не создают.

Если репозиторий не подключён — одна фраза об этом и ничего, что можно принять за нули.

### 5.7 Динамика

Процент проекта по суточным снимкам:

> 10.09 — 31% · 12.09 — 34% · 14.09 — 38% · 17.09 — 42%

Рядом за период: сколько задач подтверждено, сколько создано, сколько блокеров на задачах. Коммиты и PR в этот ряд не подмешиваются: они в блоке репозитория и при двух проектах на одном репозитории иначе посчитались бы дважды.

### 5.8 Настройки

Имя проекта, таймзона, чат, участники и роли, ветка списка дня, ветка отчётов, логин GitHub, подключённый репозиторий, время группового отчёта.

Смена таймзоны не переписывает уже отправленный список дня. Новые сутки и новый застой считаются по новой зоне.

## 6. Список задач дня

Нативный чеклист Telegram боту недоступен: `sendChecklist` требует Business-аккаунт и не работает в ветках супергруппы. Список дня — сообщение бота, которое он редактирует. Пункты отмечаются инлайн-кнопками.

Список свой у каждого исполнителя: пара «проект + исполнитель + дата» — не больше одного сообщения. Оно живёт в ветке этого исполнителя. Дата — по таймзоне проекта. У `viewer` списка нет.

- списка на сегодня нет — новое сообщение с датой в заголовке (`17.09`) и первым пунктом;
- список на сегодня уже есть — дописать пункт в то же сообщение;
- в сообщение больше не помещается — бот отказывает и говорит, что список дня заполнен. Второе сообщение на ту же дату не создаётся.

Незакрытые пункты (`IN_PROGRESS`, `BLOCKED`) на следующий день переносятся сами, с пометкой, какой это день. Пункт в `REVIEW` открытым не переносится: галочка стоит, задача ждёт руководителя и видна на экране «В работе» как ожидающая подтверждения.

Создание: формулировка, исполнитель, приоритет, «в сегодня» или «в план». Шага «выберите issue» нет. Подходящей сущности в GitHub можно не иметь.

Галочка переводит задачу в `REVIEW`. `DONE` ставит руководитель по правилу из 2.4. Пока руководитель не ответил, процент прежний.

Передача исполнителя убирает пункт из сегодняшнего списка прежнего и ставит его в сегодняшний список нового, если задача была `IN_PROGRESS` или `BLOCKED`.

## 7. Отчёты

### 7.1 Ежедневный

В личку отчёт начинается с общего прогресса по проектам этого пользователя, дальше блок на каждый его проект. GitHub вынесен вниз, по одному блоку на репозиторий, даже если репозиторием пользуются два проекта.

> ## DAILY DEVELOPMENT REPORT
> **Все проекты:** 37% → 39%
>
> ### Общественный сенсор
> **Прогресс:** 42% → 45%
>
> **За день:** ✅ подтверждено 3 · 🆕 создано 2 · ⚠️ заблокировано 1
>
> **Сейчас:** 7 — Классификация сигнала
> **Риск:** нет стабильного доступа к одному из источников данных
> **Следующий шаг:** подключить резервный источник
>
> ### GitHub `org/sensor`
> CI зелёный · смержено PR 1 · коммитов 6
> Проекты: Общественный сенсор

«В репозитории есть движение, в задачах за сутки тишина» печатается в блоке того проекта, для которого условие из 3.3 выполнено.

В групповую ветку уходит отчёт только её проекта, без строки «все проекты». Блок репозитория в группе есть: это репозиторий данного проекта.

### 7.2 Еженедельный

> ## WEEKLY DEVELOPMENT REPORT
> **Все проекты:** было 24% → стало 37%
>
> ### Общественный сенсор
> **Прогресс:** было 28% → стало 42%
>
> **Сделано:** подтверждённые за неделю задачи
> **Что замедлило разработку:** причины блокеров и строки застоя PR / CI
> **Следующая неделя:** ближайшие задачи плана
>
> ### GitHub `org/sensor`
> commits 47 · PR смержено 8 · issues закрыто 13

Числа GitHub — про репозиторий за неделю, один раз. В сумму по проектам они не входят.

### 7.3 Откуда берутся текстовые блоки

Их никто не пишет вручную.

- **Сейчас** и **Следующий шаг** — по правилам 5.1.
- **Риск** и **Что замедлило разработку** — причины блокеров задач и факты из 2.3, дословно: «PR #138 без движения 4 дня, CI красный».
- **За день** — названия задач, которые за сутки созданы или перешли в `DONE`. Это задачи, не сообщения коммитов.
- Блок **GitHub** — смерженные PR, коммиты и закрытые issues репозитория. Внутрь абзаца про задачи эти названия не подмешиваются.

Нет данных — блок не печатается. Пустой процент не заменяется нулём.

### 7.4 Доставка

- **В личку** — по команде, в любой момент (`/report`). Карточки проектов пользователя и блоки их репозиториев.
- **В группу** — по расписанию, в ветку отчётов этого проекта.

Ветка отчётов может не совпадать с ветками списков дня и хранится отдельно. На проект настраиваются время и включение групповой отправки. Личный отчёт по команде доступен и при выключенной групповой рассылке. Недельный отчёт в группу и в личку — тем же разделением, когда он включён в объём.

## 8. Архитектура

```
Telegram Bot → Bot API / Webhook → Backend → Progress Engine → PostgreSQL
                                             ├── Tasks
                                             ├── GitHub mirror (на репозиторий)
                                             ├── Event Processor
                                             └── Report Generator
GitHub: API + Webhooks → Event Processor
```

Задачи с зеркалом не соединены внешним ключом. Сопоставление человека и логина происходит в момент показа.

---

## 9. Структура данных

### repositories

`id`, `owner`, `name`, `default_branch_ci`

### projects

`id`, `name`, `description`, `repository_id` (пусто — репозиторий не подключён), `timezone`, `telegram_chat_id`, `created_at`

Один `repository_id` может стоять у нескольких проектов.

### users

`id`, `telegram_user_id`, `github_login` (пусто — сопоставления нет), `name`

Оба внешних ключа уникальны. Пустой логин уникальности не нарушает.

### project_members

`id`, `project_id`, `user_id`, `role` (`viewer` / `member` / `lead`), `topic_id` — ветка списка дня; у `viewer` пусто

### tasks

`id`, `project_id`, `number`, `title`, `description`, `status`, `priority` (`high` / `normal` / `low`), `assignee_id`, `created_at`, `updated_at`, `completed_at`

`number` уникален в проекте. Колонок issue и прогресса задачи нет. Вес не хранится.

### milestones

`id`, `repository_id`, `milestone_number`, `title`, `state`, `due_on` — зеркало GitHub, не этапы проекта

### issues

`id`, `repository_id`, `issue_number`, `title`, `state`, `assignee_login`, `closed_by_login`, `updated_at`, `closed_at`

Природный ключ — репозиторий и номер, не проект.

### issue_dependencies

`issue_id`, `depends_on_issue_id`, `link_type` (`blocked_by` / `sub_issue`) — зеркало для строки на экране GitHub

### pull_requests

`id`, `repository_id`, `pull_request_number`, `title`, `author_login`, `state`, `ci_status`, `updated_at`, `merged_at`, `merged_by_login`

### commits

`id`, `repository_id`, `sha`, `message`, `author_login`, `created_at` — хвост для экрана и блока отчёта, не журнал всей истории

### blockers

`id`, `task_id`, `reason`, `required_action`, `asked_at`, `resolved_at`

Только блокеры задач. Строки про CI и PR в эту таблицу не пишутся: они выводятся из зеркала.

### task_lists

`id`, `project_id`, `assignee_id`, `topic_id`, `message_id`, `list_date`

Уникально `project_id + assignee_id + list_date`.

### task_list_items

`id`, `list_id`, `task_id`, `position`, `is_done`, `carried_from_list_id`

### report_targets

`id`, `project_id`, `chat_id`, `topic_id`, `report_type` (`daily` / `weekly`), `schedule_cron`, `timezone` (если не задана — из проекта), `is_enabled`

### events

`id`, `source`, `event_type`, `payload`, `created_at` — журнал только дополняется

### progress_snapshots

`id`, `project_id`, `progress`, `created_at`

## 10. AI-слой

AI может пересказать уже собранные блоки отчёта обычным языком и заметить расхождение из 3.3 теми же фактами.

AI не является источником истины. Он не заводит задачи, не ставит `DONE`, не придумывает связь задачи с issue и не добавляет фактов, которых нет в задачах и в зеркале.

---

## 11. Definition of Done

Задача проекта выполнена, когда руководитель подтвердил её по правилу из 2.4 и у неё нет открытого блокера.

Смерженный PR, закрытый issue и зелёный CI таким подтверждением не являются.

---

## 12. Объём работ

### MVP

1. Карточка на проект на каждом экране; несколько проектов на одном репозитории; проект может быть без репозитория.
2. Участники, роли, доступ по составу проекта, логин GitHub у человека.
3. Задачи со статусами и приоритетом, без связи с issue.
4. Прогресс только по подтверждённым задачам; галочка процента не двигает.
5. Экраны «Прогресс», «В работе», «Сделано», «План», «Блокеры», «GitHub».
6. Блокировка задачи через два дня и вопрос исполнителю; отдельно — CI и застоявшиеся PR участников.
7. Список дня в ветке исполнителя и перенос незакрытого.
8. Ежедневный отчёт: проекты по задачам, GitHub — блоком на репозиторий.
9. Webhooks GitHub App как основной канал, опрос — только сверка пропущенного.
10. Строка расхождения «в репозитории есть движение, в задачах тишина».

Не входит в MVP: связь задачи с issue или PR, заведение задач из issues, делёж issues одного репозитория по проектам, несколько репозиториев у одного проекта, зависимости между задачами, процент по milestone, смена объектов GitHub, AI, недельный отчёт, динамика, публичный dashboard.

### Дальше

AI-пересказ блоков отчёта, недельные отчёты, динамика по снимкам, несколько репозиториев у одного проекта.

Публичный dashboard, история проекта, визуальная шкала времени, прогнозирование сроков — только как вспомогательная аналитика, без неподтверждённой точности.

## 13. Критерий успеха

> Насколько быстро человек понимает состояние разработки, не открывая GitHub и не спрашивая разработчиков.

Целевое поведение: **открыл Telegram → за 10–20 секунд понял, что сделано по задачам, что происходит сейчас, что блокирует работу и какой следующий шаг.** Картина репозитория при этом видна рядом и не подменяет собой задачи.
