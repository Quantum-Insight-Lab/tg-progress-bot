# Прогресс-бот — задачи в Telegram с интеграцией GitHub

## Цель

Приложение для ведения задач в Telegram. Задачи ведут люди в боте, а GitHub подключён как интеграция: он даёт технические факты и ссылки, но ничего не решает за людей.

Бот отвечает на вопрос:

> **Что уже сделано, что делается прямо сейчас, что мешает и какой следующий шаг?**

Разделение ответственности:

- **Telegram** — где живут задачи и где происходит работа с ними;
- **Progress Layer** — что задачи означают для проекта: прогресс, этапы, блокеры;
- **GitHub** — что изменилось в коде: issues, PR, коммиты, CI.

Главное ограничение: бот не создаёт иллюзию точности. Если реальное состояние неизвестно, показывается **«Нет данных»** или **«Требуется подтверждение»**, а не придуманный процент.

---

## 1. Основной сценарий

Пользователь открывает бота и сразу видит актуальный статус: текущий этап, общий прогресс, что сделано, что в работе, что запланировано, последние изменения, состояние GitHub и ближайший следующий шаг.

Главный экран:

> **ПРОЕКТ: Общественный сенсор**
> **Сейчас:** разработка MVP — **42%**

### Сделано
- архитектура проекта;
- структура базы данных;
- Telegram-интерфейс;
- pipeline обработки сообщений;
- GitHub CI.

### В работе
- AI-интервьюер;
- классификация сигналов.

### Далее
- кластеризация похожих сигналов;
- публичная карточка проблемы.

## 2. Данные и роли

### 2.1 Проект и этапы

Проект привязан к GitHub-репозиторию, причём в одном репозитории может жить несколько проектов, а один проект не выходит за пределы репозитория.

Этапы вручную не ведутся — это GitHub milestones: название и срок берутся из milestone, порядок — по дате завершения, закрытый milestone означает завершённый этап. Задача попадает в этап по milestone своего issue, без milestone — в «Без этапа». Один milestone может быть этапом сразу в нескольких проектах репозитория. Пример этапов: Discovery, Architecture, Core Backend, AI Pipeline, Telegram, Verification Engine, Dashboard, Pilot, Production.

Этап показывает: процент выполнения, свои задачи, блокеры, дату начала, ориентировочную дату завершения, зависимости.

У проекта есть таймзона — по ней считаются «сегодня» и границы суток для списков задач и отчётов.

### 2.2 Задача

Задача — основная сущность продукта: её создаёт и ведёт человек в боте, автоматически задачи не появляются.

Поля: ID, название, описание, проект, issue, приоритет (из него выводится вес), исполнитель, статус, прогресс, даты создания, изменения и завершения.

Статусы:

- `PLANNED` — заведена, ждёт своей очереди в плане;
- `IN_PROGRESS` — стоит в сегодняшнем списке;
- `BLOCKED` — два дня без движения, причина выясняется (см. 2.3);
- `REVIEW` — исполнитель отметил галочкой, ждёт подтверждения;
- `DONE` — руководитель подтвердил;
- `CANCELLED` — делать не будем.

При создании задача по умолчанию попадает в сегодняшний список и сразу становится `IN_PROGRESS`; её можно отложить в план, тогда это `PLANNED`. Незакрытая задача из статуса не выпадает — она переносится в список следующего дня с пометкой, какой день идёт.

Приоритет задаётся в боте: `high`, `normal`, `low`, по умолчанию `normal`. Исполнитель выбирается при создании, по умолчанию это assignee связанного issue; в GitHub назначение не пишется. Без исполнителя задача не создаётся.

Связь с issue обязательна: issue задаёт границы работы, задачи описывают её шаги, поэтому у одного issue может быть несколько задач.

### 2.3 Блокеры и застой

Задача, не отмеченная за два дня, уходит в `BLOCKED`, и бот пишет исполнителю в личку: «AI-12 не двигается 3-й день, что мешает?» — с кнопкой «нет блокера». Строка ответа становится причиной блокера, кнопка возвращает задачу в `IN_PROGRESS`. По одной задаче бот переспрашивает не чаще раза в 2 дня.

Отдельно бот показывает факты застоя из GitHub — даже если причину никто не назвал:

- PR открыт, а CI красный;
- PR висит в review без движения дольше 2 дней;
- по связанному issue нет активности дольше 2 дней;
- у issue нет ни ветки, ни PR дольше 2 дней.

Поля блокера:

- **причина** — ответ исполнителя;
- **влияние** — по связям GitHub: какие задачи ждут этот issue;
- **что требуется** — необязательно, иначе «Нет данных».

### 2.4 Участники и доступ

Участник проекта — это Telegram-аккаунт, связанный с GitHub-логином; связь нужна, чтобы понимать, кто что делает, и кому ставить задачу. Один человек может участвовать в нескольких проектах, роль задаётся в каждом отдельно.

Роли:

- `viewer` — только просмотр;
- `member` — исполнитель, имеет свою ветку (topic) для задач;
- `lead` — руководитель, подтверждает завершение задач.

Бот отвечает только участникам проекта. Остальным — отказ, без раскрытия данных.

## 3. GitHub-интеграция

Бот получает из GitHub: repository, branches, commits, pull requests, issues, labels, milestones, workflows / CI status, releases, даты изменений и авторов.

Доступ — через **GitHub App**, а не личный токен: работает с приватными репозиториями, даёт секрет для проверки webhooks и отдельные лимиты.

Обновление данных — по webhooks (`push`, `pull_request`, `issues`, `workflow_run`, `release`), чтобы не держать постоянный polling.

**Синхронизация односторонняя:** GitHub → Progress Layer. Бот не изменяет объекты GitHub — issues создаёт и закрывает человек.

### 3.1 Что даёт интеграция

- issue для задачи: его номер, название, milestone (этап) и assignee (исполнитель по умолчанию);
- связанные PR и коммиты — по ссылкам на issue:

> Реализовать голосовой ввод → Issue #52, PR #68, commits `a12f...`, `b81c...`

- зависимости: связи `blocked by` / `blocks` между issues и вложенность sub-issues. По ним считается «Влияние» блокера и порядок в плане: задача, чей issue ждёт другой, опускается ниже;
- сигналы завершения: issue закрыт или его PR смержен → незакрытые задачи этого issue уходят в `REVIEW`, issue закрыт как not planned → предлагается отмена;
- сигналы застоя и статус CI (см. 2.3).

`DONE` ставит только руководитель (`role = lead`): бот спрашивает его «Похоже, задача выполнена. Подтвердить завершение?». **Задача не закрывается на основании коммита** — commit ≠ готовый продуктовый результат.

## 4. Расчёт прогресса

Прогресс считает отдельный сервис (Progress Engine) и считает его по задачам:

`progress = вес выполненных задач / вес всех задач проекта`

Вес вручную не вводится — он выводится из приоритета задачи: `high` — 3, `normal` — 2, `low` — 1. По умолчанию `normal`, поэтому пока приоритеты не расставлены, формула совпадает с «закрытые / все» — на старте проекта это допустимо.

В прогресс попадает только то, что заведено в боте: работа, по которой задач нет, в проценте не отражается. Чтобы такие пробелы были видны, экран «GitHub» показывает issues, по которым ещё нет ни одной задачи.

Прогресс отдельной задачи не вычисляется: полоса показывается только если поле `progress` заполнено, иначе — «Нет данных».

Общий прогресс по всем проектам для отчётов считается той же формулой по задачам всех проектов сразу: шкала веса единая, поэтому суммировать корректно. Это число показывает, сколько всего работы закрыто, а не насколько близок к цели каждый проект — поэтому оно идёт строкой рядом с проектными, а не вместо них.

Значения прогресса проекта складываются в снимки (`progress_snapshots`) — из них строится динамика.

## 5. Telegram-интерфейс

Выбирать проект не нужно: каждый экран показывает по карточке на проект, в котором участвует пользователь, — сверху те, где изменения свежее. Один проект — одна карточка.

На экранах проценты разных проектов не складываются — каждая карточка живёт своим числом. Общий прогресс по всем проектам есть только в отчётах (см. 7.1 и 7.2).

Главное меню: **📊 ПРОГРЕСС**, **🔨 В РАБОТЕ**, **✅ СДЕЛАНО**, **📋 ПЛАН**, **🐙 GITHUB**, **⚠️ БЛОКЕРЫ**, **📈 ДИНАМИКА**, **⚙️ НАСТРОЙКИ**.

### 5.2 В работе

Задачи в сегодняшнем списке, для каждой:

### 5.7 Динамика

> 10.09 — 31% · 12.09 — 34% · 14.09 — 38% · 17.09 — 42%

Плюс метрики за период: закрытые и новые задачи, коммиты, PR, среднее время закрытия задачи, количество блокеров. Считаются по задачам проекта и связанным с ними issues и PR — иначе в репозитории с несколькими проектами цифры перемешаются.

## 6. Список задач дня

Нативный чеклист Telegram боту недоступен: `sendChecklist` требует подключённого Business-аккаунта и не поддерживает ветки супергруппы. Поэтому список дня — обычное сообщение бота, которое он редактирует, а пункты отмечаются инлайн-кнопками.

Список живёт в ветке (topic) ответственного по проекту.

Правило одного списка на день (дата — по таймзоне проекта):

- списка с сегодняшней датой нет → отправить новое сообщение с заголовком-датой (`17.09`) и первым пунктом-задачей;
- список с сегодняшней датой уже есть → дописать задачу пунктом в то же сообщение.

Незакрытые пункты прошлого дня переносятся в новый список автоматически, с пометкой, какой день идёт.

При создании задачи пользователь формулирует её, выбирает issue из репозитория, исполнителя и приоритет. Если подходящего issue нет, его сначала создают в GitHub — без issue задача не создаётся.

Нажатие кнопки-галочки переводит задачу в `REVIEW`; `DONE` подтверждает руководитель. Issue бот не закрывает.

## 7. Отчёты

### 7.1 Ежедневный

Отчёт начинается со строки общего прогресса по всем проектам, дальше идёт блок на каждый проект:

> ## DAILY DEVELOPMENT REPORT
> **Все проекты:** 37% → 39%
>
> ### Общественный сенсор
> **Прогресс:** 42% → 45%
>
> **За день:** ✅ закрыто 3 · 🔨 начато 2 · ⚠️ заблокировано 1
>
> **Что изменилось:** добавлен AI-классификатор; подключена обработка voice messages; создан PR для verification engine.
>
> **Сейчас:** Verification Engine
> **Риск:** один источник данных нестабилен
> **Следующий шаг:** подключить резервный источник

### 7.2 Еженедельный

> ## WEEKLY DEVELOPMENT REPORT
> **Все проекты:** было 24% → стало 37%
>
> ### Общественный сенсор
> **Прогресс:** было 28% → стало 42%
>
> **Сделано:** список подтверждённых задач
> **Что замедлило разработку:** сигналы и блокеры за неделю
> **Главные блокеры:** активные блокеры по влиянию
> **Следующая неделя:** ближайшие задачи из плана
> **GitHub:** commits 47 · PR 8 · issues closed 13

### 7.3 Откуда берутся текстовые блоки

Вручную их никто не заполняет, всё выводится из данных:

- «Сейчас» — задача с самым свежим изменением, при равенстве — с наибольшим весом;
- «Следующий шаг» — первая задача из плана, у которой зависимости уже закрыты;
- «Риск» и «Что замедлило разработку» — блокеры и факты застоя, конкретным фактом: «PR #138 без движения 4 дня, CI красный».

Если данных нет, блок не печатается. С V2 AI переформулирует эти блоки человеческим языком, не добавляя фактов, которых нет в данных.

### 7.4 Доставка

- **в личку** — по команде пользователя в любой момент (`/report`, а `/weekly` — с V2), карточкой на каждый его проект;
- **в группу** — автоматически по расписанию (cron), в ветку для отчётов и только по её проекту.

Ветка для отчётов может не совпадать с ветками задач участников, поэтому хранится отдельно. На проект настраиваются время, таймзона и включение групповой отправки; личный отчёт по команде доступен всегда, даже если групповая рассылка отключена.

## 9. Структура БД

### projects
`id`, `name`, `description`, `repository`, `timezone`, `telegram_chat_id`, `created_at`

### users
`id`, `telegram_user_id`, `github_login`, `name`

### project_members
`id`, `project_id`, `user_id`, `role` (`viewer` / `member` / `lead`), `topic_id` — ветка задач участника

### stages
`id`, `project_id`, `milestone_number`, `name`, `order`, `status`, `due_on` — зеркало GitHub milestones

### tasks
`id`, `project_id`, `issue_id`, `title`, `description`, `status`, `priority` (`high` / `normal` / `low`), `assignee_id`, `progress` (может быть пустым), `created_at`, `updated_at`, `completed_at` — вес не хранится, считается из приоритета

### issues
`id`, `project_id`, `stage_id` (пусто — «Без этапа»), `issue_number`, `title`, `state`, `assignee_id`, `closed_at`, `updated_at` — кэш GitHub, нужен для ссылок, этапа и сигналов

### issue_dependencies
`issue_id`, `depends_on_issue_id`, `link_type` (`blocked_by` / `sub_issue`) — зеркало связей GitHub

### issue_pull_requests
`id`, `issue_id`, `pull_request_number`

### blockers
`id`, `task_id`, `source` (`stale` / `declared`), `signal_type`, `reason` (пусто для `stale`), `impact`, `required_action`, `detected_at`, `asked_at`, `resolved_at`

### task_lists
`id`, `project_id`, `topic_id`, `message_id`, `list_date` — уникально на пару проект + дата

### task_list_items
`id`, `list_id`, `task_id`, `position`, `is_done`, `carried_from_list_id`

### report_targets
`id`, `project_id`, `chat_id`, `topic_id`, `report_type` (`daily` / `weekly`), `schedule_cron`, `timezone` (если не задана — из проекта), `is_enabled`

### events
`id`, `source`, `event_type`, `payload`, `created_at`

### progress_snapshots
`id`, `project_id`, `progress`, `created_at`

## 10. AI-слой

AI применим для: анализа commit messages, поиска потенциально завершённых задач, поиска расхождений между задачами и GitHub, объяснения состояния простым языком, формулировок в отчётах.

AI не является источником истины: в отчётах он только переформулирует уже выведенные из данных факты.

---

## 11. Definition of Done

Задача выполнена, когда код реализован, нужные тесты проходят, PR принят, завершение подтверждено руководителем, известных блокеров нет и результат соответствует ожидаемому поведению.

## 12. Объём работ

### MVP

1. Telegram-бот, карточка на проект на каждом экране, в том числе несколько проектов в одном репозитории;
2. участники, роли и доступ по whitelist;
3. задачи со статусами, приоритетом и обязательной связью с issue;
4. расчёт прогресса и подтверждение завершения руководителем;
5. экраны «Прогресс», «В работе», «Сделано», «План», «Блокеры», «GitHub»;
6. блокировка задачи через два дня и вопрос исполнителю о причине;
7. список задач дня в ветке с переносом незакрытого;
8. ежедневный отчёт;
9. GitHub webhooks как основной канал синхронизации, опрос — только сверка пропущенного.

Не входит в MVP: сложная аналитика, несколько репозиториев на один проект, сложный AI-анализ, публичный dashboard, автоматическое изменение статусов без подтверждения.

### V2

AI-анализ коммитов; AI-формулировки блоков отчёта; автоматические предложения по статусам; динамика; недельные отчёты; несколько репозиториев.

### V3

Публичный dashboard; история проекта; визуальный timeline; AI Project Manager; прогнозирование сроков — только как вспомогательная аналитика, без неподтверждённой точности.

## 13. Критерий успеха

> Насколько быстро человек понимает состояние разработки, не открывая GitHub и не спрашивая разработчиков.

Целевое поведение: **открыл Telegram → за 10–20 секунд понял, что сделано, что происходит сейчас, что блокирует работу и какой следующий шаг.**
