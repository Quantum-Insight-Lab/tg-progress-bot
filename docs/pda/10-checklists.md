## Стартовый аудит (П1)

Кода домена ещё нет, поэтому часть цифр нулевая по определению: это и есть базовая линия.

| Вопрос | На старте | Что означает |
| --- | --- | --- |
| Сколько инвариантов домена сформулировано? | 28 | больше пяти: домен описан, патч применим |
| Сколько из них имеет тест? | 0 | долг S-7 — 28, закрывается по issues |
| Сколько `event_type` в коде и в реестре? | 0 мимо реестра, 42 в реестре | типы только сгенерированные |
| Есть ли импорты из домена в инфраструктуру? | 0 | границы введены до первой фичи |
| Сколько реализаций у конфигурации, часов, клиента БД? | по одной у конфигурации и часов, клиента БД ещё нет | дрейф не начался |
| Сколько ждёт исполнитель решения по домену? | не измеряется | один исполнитель, см. [00](00-README.md) |

**Базовая линия:** 28 инвариантов в спеке, 0 в тестах, 0 событий мимо реестра. Через месяц разработки к ней возвращаются: любое соотношение, кроме «28, 28, 0», — долг, а не «так вышло».

## Порядок входа в разработку

1. Опубликовать backlog: `npm run backlog:publish` — план, `-- --apply` — запись; после этого на закрытии issue работает страж TR-7.
2. M1: журнал событий с идемпотентностью и схемами из реестра (I-01), процесс и webhook Telegram (I-02).
3. Дальше — по `blocked_by`: люди и проекты, затем задачи с канвасом и зеркало GitHub параллельно по контекстам, прогресс, отчёты, запуск.
4. После первых 5–10 issues — первое значение `underdelivery_rate`: по нему калибруется `MAX_ATOMS_PER_STEP` и степень надзора за исполнителем.
