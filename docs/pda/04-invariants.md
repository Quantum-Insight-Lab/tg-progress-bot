> Invariant Spec Sheets (PDA 5.3, шаг 4). Каждый инвариант имеет механизм обеспечения и тест, ссылающийся на его ID (патч S-7).

# Инварианты домена

Названия тестов начинаются с ID: `INV-04 lead-only confirmation`. Скрипт сверки в CI сравнивает список ID здесь со списком ID в тестах; расхождение ломает сборку.

## Сводная таблица

| ID | Формулировка | Механизм обеспечения | Слой |
| --- | --- | --- | --- |
| INV-01 | Задача всегда ссылается на существующий issue своего проекта | `NOT NULL` + FK, `createTask` / `pickIssueFromMirror` по зеркалу проекта | БД + домен |
| INV-02 | У задачи всегда есть исполнитель, и он участник проекта | `NOT NULL` + FK, валидатор сверяет `project_members` | БД + домен |
| INV-03 | Задача имеет ровно один статус, переходы только по таблице переходов | тип-перечисление, единственная функция перехода, property-based тест | домен |
| INV-04 | Статус `DONE` присваивается только по акту участника с ролью `lead` | проверка роли внутри функции перехода, не в хендлере | домен |
| INV-05 | Задача не может быть `DONE` при активном блокере | валидатор перехода: подтверждение закрывает блокеры одной транзакцией | домен |
| INV-06 | На пару «проект + дата» существует не более одного списка | `UNIQUE (project_id, list_date)` | БД |
| INV-07 | Пункт списка ссылается на задачу того же проекта | валидатор + проверка при вставке (составной FK через `project_id`) | БД + домен |
| INV-08 | Повторная доставка одного факта не создаёт второго события и не меняет состояние | `UNIQUE (idempotency_key)` в журнале, обработчики идемпотентны | БД + домен |
| INV-09 | Бот не изменяет объекты GitHub | GitHub Adapter не содержит вызовов мутаций; тест на отсутствие write-методов Octokit | инфраструктура |
| INV-10 | Прогресс проекта считается только по задачам этого проекта | `progressOfProject` фильтрует по `project_id`; общий процент — только `progressOfAllProjectsForReport` | домен |
| INV-11 | Процент не показывается, если знаменатель пуст | `progressOfProject` возвращает `null`, `formatProgress` печатает «Нет данных»; `dynamicsSeries` не интерполирует | домен + UI |
| INV-12 | Любой доступ к данным проекта проходит проверку членства | единственный guard на входе в хендлеры, тест перебирает все зарегистрированные хендлеры | домен |
| INV-13 | Статус `BLOCKED` существует ровно при активном блокере; снятие возвращает `IN_PROGRESS` | обе операции выполняются одной функцией перехода, тест на симметрию | домен |
| INV-14 | У задачи не более одного незакрытого пункта во всех списках | частичный уникальный индекс `WHERE is_done = false` | БД |
| INV-15 | Вес задачи — функция приоритета и нигде не хранится | вес вычисляется одной функцией, поля `weight` в схеме нет, тест на соответствие таблице | домен |
| INV-16 | Журнал событий только дополняется | права БД без `UPDATE` и `DELETE` на таблицу, тест на попытку правки | БД |

Шестнадцать инвариантов при рекомендованных методологией 5–15: перебор на один пункт допущен сознательно, потому что INV-16 относится к журналу, а не к предметной области, и удалять его ради круглого числа нельзя.

## Развёрнутые карточки

Расписаны четыре инварианта, нарушение которых не ловится тестами домена «по дороге»: они защищают доверие к продукту и права доступа.

### INV-04 — подтверждать может только руководитель

| Поле | Значение |
| --- | --- |
| Формулировка | Переход задачи в `DONE` возможен только по акту участника с ролью `lead` в проекте этой задачи |
| Сфера действия | Task, ProjectMember; акт A-3 |
| Что считается нарушением | исполнитель подтверждает свою же задачу; подтверждение приходит от `lead` другого проекта; `DONE` выставляется обработчиком события GitHub |
| Механизм | роль проверяется внутри функции перехода статуса, а не в обработчике кнопки: любой путь к `DONE` проходит через одну проверку |
| Где проверяем | домен |
| Тесты | сценарный: подтверждение от `member` отклонено; от `lead` другого проекта отклонено; property-based: ни одна последовательность событий GitHub не приводит к `DONE` |
| Мониторинг | счётчик `rejected_commands` с причиной `role_denied` |
| Реакция | отклонённая попытка — норма; всплеск означает, что людям непонятно, кто подтверждает, и это вопрос к UX, а не к коду |
| Владелец | архитектор |

### INV-08 — один факт применяется один раз

| Поле | Значение |
| --- | --- |
| Формулировка | Повторная доставка webhook, повторное нажатие кнопки или повторный запуск задания не создают второго события и не меняют состояние |
| Сфера действия | все события; интеграция с GitHub; инлайн-кнопки; планировщик |
| Что считается нарушением | два `task.checked` по одному нажатию; двойной снимок прогресса за день; двойная отправка отчёта; задача, перенесённая дважды в один список |
| Механизм | у каждого события есть `idempotency_key` с уникальным индексом; ключи: `delivery_id` для webhook, `callback_query_id` для кнопки, `project_id + date` для снимка и отчёта, `task_id + list_date` для переноса |
| Где проверяем | БД (уникальный индекс) и домен (обработчик проверяет результат вставки) |
| Тесты | property-based: повторная подача любого события не меняет состояние; сценарный: две доставки одного webhook дают один эффект |
| Мониторинг | `duplicate_deliveries` — число отброшенных повторов; норма — больше нуля, это признак работающей защиты |
| Реакция | ноль повторов за неделю означает, что защита не срабатывала ни разу: нужно проверить, что ключи действительно проставляются |
| Владелец | архитектор |

### INV-11 — процент не выдумывается

| Поле | Значение |
| --- | --- |
| Формулировка | Если по проекту нет ни одной задачи, процент не показывается: вместо числа печатается «Нет данных» |
| Сфера действия | экран прогресса, карточка проекта, оба отчёта, динамика |
| Что считается нарушением | вывод 0% при отсутствии задач; вывод 100%, когда закрыта одна задача из одной, а незаведённой работы больше; интерполяция значений в динамике между снимками |
| Механизм | функция расчёта возвращает `null` при пустом знаменателе, тип результата `number \| null` заставляет обработать оба случая на уровне компилятора |
| Где проверяем | домен, плюс типы на границе с представлением |
| Тесты | `INV-11`: пустой проект даёт `null`; в динамике пропуски не заполняются |
| Мониторинг | доля issues без задач (`coverage_gap`) — показывает, насколько процент вообще отражает объём работы |
| Реакция | при `coverage_gap` выше половины процент перестаёт быть информативным: в отчёте рядом с ним печатается предупреждение |
| Владелец | архитектор |

### INV-12 — доступ только участникам

| Поле | Значение |
| --- | --- |
| Формулировка | Любая операция чтения или записи данных проекта требует записи в `project_members` для этого пользователя |
| Сфера действия | все хендлеры бота, все команды, все инлайн-кнопки, личные отчёты |
| Что считается нарушением | ответ постороннему на `/report`; данные проекта в кнопке, доставшейся не участнику; доступ по устаревшему членству |
| Механизм | единственная точка авторизации на входе в хендлер; хендлеры регистрируются через фабрику, которая guard навешивает сама, поэтому обойти его нельзя, забыв строку |
| Где проверяем | домен, на входе |
| Тесты | тест перебирает реестр хендлеров и проверяет, что каждый обёрнут guard'ом: новый хендлер без проверки ломает сборку |
| Мониторинг | `rejected_commands` с причиной `not_a_member` |
| Реакция | всплеск означает либо утечку ссылки на бота, либо удалённого участника, который продолжает нажимать кнопки |
| Владелец | архитектор |

## Таблица переходов статуса задачи

Единственный разрешённый набор переходов; всё остальное отклоняется функцией перехода (INV-03).

| Из | В | По акту | Условие |
| --- | --- | --- | --- |
| — | `IN_PROGRESS` | A-1 создание задачи | задача попадает в сегодняшний список |
| — | `PLANNED` | A-1 + A-9 создание в план | задача в очередь, без списка дня |
| `PLANNED` | `IN_PROGRESS` | A-1 постановка в список дня | — |
| `IN_PROGRESS` | `BLOCKED` | A-13 автоматически | нет отметки дольше `STALE_DAYS`, есть активный блокер |
| `BLOCKED` | `IN_PROGRESS` | A-5 «нет блокера», A-4 после снятия | активных блокеров не осталось |
| `IN_PROGRESS` | `REVIEW` | A-2 галочка | — |
| `BLOCKED` | `REVIEW` | A-2 галочка | блокеры закрываются в той же транзакции |
| `REVIEW` | `IN_PROGRESS` | снятие галочки | — |
| `REVIEW` | `DONE` | A-3 подтверждение | роль `lead`, активных блокеров нет (INV-04, INV-05) |
| любой кроме `DONE` | `CANCELLED` | A-6 отмена | — |
| `DONE` | — | — | терминальный: изменение только через новую задачу |
