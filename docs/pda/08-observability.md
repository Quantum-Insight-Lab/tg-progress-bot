# Наблюдаемость

## Дашборд устойчивости

### Снижение неопределённости

| Метрика | Как считается | Норма и о чём говорит |
| --- | --- | --- |
| `time_to_clarity_blocker` | от `blocker.detected` до `blocker.declared` или `blocker.dismissed` | часы, не дни. Растёт — механизм вопросов не работает, U-3 не закрывается |
| `time_to_confirmation` | от `task.checked` до `task.confirmed` | около суток. Растёт — руководитель стал узким местом, задачи висят в `REVIEW` |
| `answer_rate` | доля вопросов о блокере, получивших любой ответ | выше 80%. Падает — бота перестали читать, пора смотреть на C-1 и C-2 |
| `dismiss_rate` | доля ответов «нет блокера» | ниже 50%. Выше — порог `STALE_DAYS` занижен, бот дёргает зря |

### Доверие данных

| Метрика | Как считается | Норма |
| --- | --- | --- |
| `coverage_gap` | доля незакрытых issues проекта, по которым нет ни одной задачи | чем ниже, тем ближе процент к реальности. Выше `coverageGapWarnRatio` (50%) — рядом с процентом печатается предупреждение (INV-11) |
| `duplicate_deliveries` | число отброшенных повторов по `idempotency_key` | больше нуля: это признак работающей защиты. Ноль за неделю — проверить, что ключи проставляются |
| `github_sync_lag` | возраст самых свежих данных из GitHub | при живых webhooks — секунды. Выше C-6 значит webhook молчит и работает только сверка |
| `orphan_signals` | сигналы застоя по issues, у которых нет задач | показывают работу вне учёта, ту же проблему, что `coverage_gap`, но с другой стороны |

### Инварианты

| Метрика | Как считается | Норма |
| --- | --- | --- |
| `invariant_violations` | нарушения, дошедшие до состояния (доменный инцидент) | строго ноль |
| `rejected_commands` | отклонённые команды с причиной: `role_denied`, `not_a_member`, `invalid_transition`, `list_full` | больше нуля — норма, это работа защиты. Всплеск конкретной причины — вопрос к UX, а не к коду |
| `structural_coverage` | тесты с ID / инварианты в спеке | 100%, иначе долг (S-7) |
| `registry_drift` | `event_type` в коде мимо реестра | ноль (S-3) |

### Надёжность

| Метрика | Норма |
| --- | --- |
| `telegram_api_errors` по кодам | важны отдельно `400` при редактировании списка дня (длина сообщения, C-5) и `429` |
| `github_rate_remaining` | не ниже 20% лимита к концу интервала |
| `scheduler_missed_runs` | ноль: пропущенный прогон — это неотправленный отчёт или несделанный снимок |
| `report_delivery_failures` | ноль, с разбивкой на личку и группу |

### Сборка

Слой из патча 9.10, сокращённый под одного исполнителя: `boundary_violations` и `duplicate_implementations` отслеживаются, `graph_change_lead_time` не отслеживается — очереди за решением архитектора нет.

| Метрика | Как считается | Норма |
| --- | --- | --- |
| `boundary_violations` | отклонённые попытки нарушить границы слоёв за период | падает со временем. Стабильно высокая по одной границе означает, что граница проведена не по реальному шву |
| `duplicate_implementations` | число механизмов из реестра `AGENTS.md`, реализованных более одного раза | ноль (S-4) |

## Доменные инциденты

Доменный инцидент — не пятисотка. Это состояние, в котором факты системы противоречат друг другу. Отдельный класс нужен, чтобы качество домена было измеримым (PDA A2).

| Класс | Пример | Реакция |
| --- | --- | --- |
| Нарушение инварианта дошло до состояния | задача `DONE` с активным блокером (INV-05) | остановить обработку, зафиксировать, восстановить состояние переигрыванием журнала, добавить тест на конкретный случай |
| Двойное применение факта | два снимка прогресса за день, две отправки одного отчёта (INV-08) | найти отсутствующий ключ идемпотентности, добавить уникальный индекс, удалить дубль |
| Расхождение с GitHub | issue закрыт неделю назад, задачи висят в `IN_PROGRESS` | проверить синхронизацию, догнать состояние, посмотреть `github_sync_lag` |
| Список дня рассинхронизирован | сообщение не отражает задачи в БД, редактирование падает | пересобрать `today_list` из журнала, проверить C-5 |
| Потеря доступа | участник удалён, но продолжает получать отчёты (INV-12) | отозвать доставку, проверить `access_list` |

Runbook на инцидент: зафиксировать факт события в журнале, определить затронутый инвариант, восстановить состояние пересборкой проекции, добавить тест с ID инварианта, и только потом закрывать инцидент. Порядок важен: тест без фиксации причины закрепляет симптом.

## Алерты

Алертов намеренно мало: бот не критичен по времени, и ночные оповещения о нём вредны.

| Условие | Куда | Почему |
| --- | --- | --- |
| `invariant_violations > 0` | сразу руководителю | домен противоречив, дальше данные только испортятся |
| `report_delivery_failures > 0` за прогон | сразу | отчёт не пришёл, а на него рассчитывают |
| `scheduler_missed_runs > 0` | сразу | планировщик — единственный источник автоматики |
| `github_rate_remaining < 20%` | дневная сводка | запас есть, реакция может подождать |
| `coverage_gap > 50%` | недельная сводка | это разговор о процессе, а не инцидент |

## Контур обратной связи

Метрики нужны, чтобы менять решения, а не чтобы висеть на дашборде. Три связки, которые проверяются раз в месяц:

1. `dismiss_rate` и `answer_rate` → пересмотр `STALE_DAYS` и `RE_ASK_DAYS` ([05](05-constants.md), C-1, C-2).
2. Доля задач с приоритетом по умолчанию → пересмотр `PRIORITY_WEIGHTS` или отказ от весов вовсе.
3. `boundary_violations` по границам → пересмотр самих границ в [07](07-architecture.md): упорно нарушаемая граница обычно проведена неправильно.
