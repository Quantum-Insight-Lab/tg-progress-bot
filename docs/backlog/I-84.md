# I-84. infra — backlog и ветки: состояние issues и одна ветка-источник

## Уже есть

- I-83 — приёмка по критерию успеха · M-1, M-2

## Зачем

Приёмка сверяет файлы backlog с GitHub и кодом. Пока у файлов нет номеров, а ветки расходятся, `tz:trace` не видит issues на GitHub, а повторная публикация создаёт дубликаты.

## Что найдено

- на GitHub #64…#146 закрыты, открытых issues нет; на `main` у файлов было `state: open` и не было `github: N` — поправлено при нарезке M8: `state: closed` и номера I-01…I-83 → #64…#146, сверены с заголовками на GitHub;
- номера были только на `dev` (acb1296); `dev` отстаёт от `main` на 211 коммитов;
- на `v2-from-spec` есть то, чего нет на `main`: правило «Уже есть» с проверкой TR-2 (8cf3080) и перезапись тела опубликованной issue (b7dffcf), PR #154 и #163; сама ветка отстаёт от `main` на 212 коммитов;
- `BRANCH` в `scripts/backlog-publish.ts` — `v2-from-spec`: ссылки «Источник» в телах 83 issues ведут на отставшую ветку, файлов M8 там нет вовсе;
- `gh` на сервере развёртывания не авторизован: сухой прогон `backlog:publish` там не запускается.

## Сделать

- решение владельца, какая ветка — источник backlog и кода:
  - `main`: перенести на неё 8cf3080 и b7dffcf, `BRANCH = 'main'`, `dev` и `v2-from-spec` закрыть — ссылки 83 issues обновит перезапись тела;
  - `v2-from-spec`: влить в неё `main` до публикации M8 — ссылки остаются, но ветка кода и ветка документов расходятся снова при следующем merge в `main`;
- после решения — `npm run backlog:publish` сухим прогоном: создать milestone «v2 · M8 Приёмка» и issues I-84…I-93; у 83 опубликованных — ни одной новой;
- `--apply` — только с подтверждением владельца: это запись в GitHub.

## Не делать

- переписывать тела закрытых issues до решения по ветке.
