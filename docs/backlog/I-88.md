# I-88. infra — логи Telegram: обновление, обработчик, исход, Bot API

## Уже есть

- I-10 — guard доступа: бот отвечает только корню и участникам · A-34 · INV-16 · события `access.denied`
- I-85 — логгер: механизм, уровень info, вход и ход процесса · B-17 · B-2, B-3 · S-4 · M-18 · A-28, A-29, A-30, A-31, A-32, A-33, A-35, A-36, A-42, A-44, A-45 · события `scheduler.missed`

## Зачем

Путь человека — обновление → guard → акт домена → событие → правка канваса ([07](../pda/07-architecture.md), «Потоки»). Строка на каждом шаге показывает, где путь оборвался: на guard, на отказе домена или на ошибке Bot API.

## Что найдено

- обработчики лежат в `src/telegram` и служат проектам, задачам и отчётам; `src/telegram` не импортирует `src/infrastructure` — логгер приходит параметром;
- `command.rejected` пишется только для причин «нет права» и «запрещённый переход»; прочие коды `DomainError` становятся ответом человеку без следа в процессе;
- ошибки Bot API пишутся событием `telegram.api_failed`, в логе их нет.

## PDA

B-17 · B-1, B-2, B-6, B-12 · INV-16 · M-12, M-15 · события `access.denied`, `command.rejected`, `telegram.api_failed`

## Атомы ТЗ

Нет: работа derived, её содержание — элементы PDA выше.

## Сделать

- обновление: `update_id`, вид, чат и его тип, топик, отправитель; какой обработчик взял обновление или что обработчика нет;
- решение guard: пропустил или отказал (INV-16), отказ — `info`;
- исход: ответ отправлен, отказ домена с кодом `DomainError` — `info`, исключение — `error` с причиной;
- вызов Bot API: метод, чат, успех или `error_code`, `retry_after` у `429`; отказ правки rich message — `warn`;
- команда и вид callback пишутся всегда, текст людей — по решению из I-85.

## Не делать

- переносить проверки guard и домена в хендлер ради строки лога (запрет 3).

## DoD

- тест по всем обработчикам бота: обновление от постороннего, отказ домена и ошибка Bot API дают по строке своего уровня;
- `npm run ci` зелёный, ни одна проверка не ослаблена.
