> Constant Cards (PDA 5.4, шаг 5). Константы конфигурируемы, но не произвольны: у каждой есть назначение, диапазон и способ калибровки.

# Константы и поверхности управления

Все значения читаются только из конфигурационного слоя (патч S-8). Магическое число в домене — ошибка сборки, список легальных исключений — в [09](09-structural-invariants.md).

Разделение по природе: C-1…C-4 — константы продукта, они влияют на поведение людей и калибруются наблюдением; C-5…C-7 — константы надёжности, они определяются ограничениями внешних систем.

## C-1 — STALE_DAYS

| Поле | Значение |
| --- | --- |
| Тип | порог |
| Зачем нужна | удерживает связь между списком дня и реальностью: задача, которая не двигается, должна объявить причину, а не тихо висеть |
| Значение по умолчанию | 2 дня |
| Допустимый диапазон | 1–5 дней |
| Как калибруем | по доле вопросов, на которые ответили «нет блокера»: если она выше половины, порог занижен и бот дёргает людей зря |
| Риск, если завышена | блокер всплывает, когда неделя уже потеряна — продукт не решает U-3 |
| Риск, если занижена | бот превращается в источник шума, люди начинают отвечать «нет блокера» механически, и ответы теряют смысл |
| Владелец | архитектор |

Один порог используется для всех сигналов застоя: отметки задачи, активности по issue, висящего PR, отсутствия ветки. Разные пороги на каждый сигнал дали бы четыре ручки настройки вместо одной, а различать их по смыслу пока не на чем.

## C-2 — RE_ASK_DAYS

| Поле | Значение |
| --- | --- |
| Тип | интервал |
| Зачем нужна | ограничивает частоту повторных вопросов по одной задаче, чтобы не превратить личку в напоминалку |
| Значение по умолчанию | 3 дня |
| Допустимый диапазон | 2–7 дней, не меньше `STALE_DAYS` |
| Как калибруем | по доле вопросов без ответа: растёт — интервал слишком мал, люди перестали читать |
| Риск, если завышена | причина блокера устаревает, в отчётах висит неактуальный текст |
| Риск, если занижена | бот выглядит навязчивым, вопросы игнорируются, и механизм перестаёт работать целиком |
| Владелец | архитектор |

## C-3 — PRIORITY_WEIGHTS

| Поле | Значение |
| --- | --- |
| Тип | коэффициенты |
| Зачем нужна | превращает приоритет в вес, чтобы крупная и мелкая задача не давали одинаковый вклад в прогресс |
| Значение по умолчанию | `high` — 3, `normal` — 2, `low` — 1 |
| Допустимый диапазон | целые 1–5, порядок строго возрастающий |
| Как калибруем | сравнением динамики прогресса с ощущением руководителя: если процент скачет от закрытия мелочей, разрыв между `high` и `low` мал |
| Риск, если разрыв велик | одна крупная задача определяет почти весь процент, остальное не видно |
| Риск, если разрыв мал | прогресс вырождается в «закрытые / все», приоритет перестаёт влиять |
| Владелец | архитектор |

Шкала единая для всех проектов: только поэтому общий процент по всем проектам в отчётах имеет смысл (ТЗ 4). Проектные веса сделали бы суммирование некорректным.

## C-4 — DEFAULT_PRIORITY

| Поле | Значение |
| --- | --- |
| Тип | значение по умолчанию |
| Зачем нужна | задача создаётся за секунды, и приоритет нельзя делать обязательным полем |
| Значение по умолчанию | `normal` |
| Допустимый диапазон | одно из трёх значений |
| Как калибруем | по доле задач, у которых приоритет так и остался значением по умолчанию: если это почти все задачи, прогресс считается по количеству, и об этом надо честно сказать в отчёте |
| Риск при `high` | всё становится важным, вес перестаёт различать |
| Риск при `low` | закрытие настоящей работы почти не двигает процент |
| Владелец | архитектор |

## C-5 — DAY_LIST_MAX_ITEMS

| Поле | Значение |
| --- | --- |
| Тип | лимит |
| Зачем нужна | список дня — одно редактируемое сообщение, а у Telegram есть предел 4096 символов; при его превышении редактирование падает с ошибкой |
| Значение по умолчанию | 30 пунктов |
| Допустимый диапазон | 10–50, с проверкой фактической длины текста перед отправкой |
| Как калибруем | по длине реальных формулировок: лимит пунктов — грубая защита, точная проверка идёт по символам |
| Риск, если завышена | сообщение перестаёт редактироваться, список дня ломается в середине дня |
| Риск, если занижена | задачу нельзя поставить, хотя день ещё не заполнен |
| Владелец | техлид |

Поведение при достижении лимита: бот отказывает в постановке и говорит, что список дня заполнен. Второе сообщение на ту же дату создавать нельзя — это нарушит INV-06.

## C-6 — GITHUB_RECONCILE_INTERVAL

| Поле | Значение |
| --- | --- |
| Тип | интервал |
| Зачем нужна | основная доставка — webhooks GitHub App. Опрос нужен только чтобы догнать пропущенную доставку (бот был недоступен, GitHub не доставил, секрет сменился) |
| Значение по умолчанию | 30 минут |
| Допустимый диапазон | 15–120 минут |
| Как калибруем | по `github_sync_lag` и числу событий, которые пришли опросом, а не webhook: если таких почти нет — интервал можно увеличить |
| Риск, если завышена | после простоя зеркало долго остаётся дырявым |
| Риск, если занижена | расход лимита API впустую при живых webhooks, вплоть до `429` |
| Владелец | техлид |

## C-7 — REPORT_SCHEDULE

| Поле | Значение |
| --- | --- |
| Тип | расписание |
| Зачем нужна | отчёт полезен в момент, когда его читают: слишком рано — день ещё не начался, слишком поздно — решение уже принято без него |
| Значение по умолчанию | ежедневный в 09:00 по таймзоне проекта, недельный в пятницу в 18:00 |
| Допустимый диапазон | любое время, хранится как cron на `report_targets` |
| Как калибруем | по времени открытия отчёта: если его читают через несколько часов, время выбрано неудачно |
| Риск при раннем времени | в отчёте нет сегодняшней активности, только вчерашняя |
| Риск при позднем времени | отчёт превращается в архив |
| Владелец | руководитель проекта |

## Границы суток

Отдельная величина, от которой зависят и `STALE_DAYS`, и «сегодня» в списке дня, и оба отчёта, — таймзона проекта (`projects.timezone`). Она не константа в смысле PDA, а часть конфигурации проекта, но упомянута здесь, потому что ошибка в ней ломает три механизма одновременно: список дня создаётся дважды за сутки, застой считается неверно, отчёт приходит не тогда, когда ждут.
