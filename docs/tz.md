# Прогресс-бот

{R-067} Задача — шаг, который человек ведёт в Telegram. {R-068} GitHub — зеркало репозитория:

- {R-069} issues;
- {R-070} PR;
- {R-071} коммиты;
- {R-072} CI;
- {R-073} milestones.

{R-074} Общее между ними два: {R-075} человек (аккаунт Telegram и логин GitHub) {R-076} и проект (к нему подключён репозиторий). {R-077} Issue не является родителем задачи {R-078} и не каталог, из которого задачу заводят. {R-079} Линейка проекта — список issues репозитория: сколько уже закрыто {R-080} и сколько ещё осталось. {R-081} Задачи этот процент не двигают.

## Цель

{R-082} Приложение для ведения задач в Telegram. {R-083} Задачи ведут люди в топике исполнителя. {R-084} GitHub подключён как интеграция: {R-085} он показывает, что происходит в репозитории, {R-086} и не решает за людей, какая задача выполнена.

{ctx} Бот отвечает на вопрос:

> - {R-087} **Что уже сделано,**
> - {R-088} **что делается прямо сейчас,**
> - {R-089} **что мешает**
> - {R-090} **и какой следующий шаг?**

{ctx} Разделение ответственности:

- {R-091} **Telegram** — где живут задачи и где с ними работают;
- {R-092} **Progress Layer** — доля закрытого бэклога репозитория {R-093} и что из issues на ком висит;
- {R-094} **GitHub** — источник этой линейки {ctx} и картина кода:
  - {R-095} issues;
  - {R-096} PR;
  - {R-097} коммиты;
  - {R-098} CI.

{R-099} Бот не создаёт иллюзию точности. {R-100} Если реальное состояние неизвестно, показывается **«Нет данных»**, {R-101} а не придуманный процент.

## 1. Основной сценарий

{R-102} Человек открывает свой топик в группе проекта. {R-103} Там канвас — одно сообщение бота на день; {R-150} другие сообщения бота в этом топике допустимы. {R-104} Меню в личке нет. {R-326} Задачу он заводит командой `/task <формулировка>` в этом же топике, {R-106} и она появляется на канвасе.

> {R-107} **ПРОЕКТ: Общественный сенсор** · {R-108} 17.09
> {R-109} **Сделано по проекту:** 42% · {R-110} осталось 18 из 31
> {R-111} **Андрей по issues:** {R-112} сделал 4 · {R-113} сейчас на нём 2 · {R-114} дальше в репозитории 16
>
> {R-115} **Сделано**
> - {R-116} #4 архитектура проекта;
> - {ctx} #8 структура базы данных;
> - {ctx} #11 Telegram-интерфейс.
>
> {R-117} **В работе**
> - {R-118} #40 классификация сигналов {R-119} — Андрей;
> - {ctx} #44 AI-интервьюер — Мария.
>
> {R-120} **Далее**
> - {R-121} #51 кластеризация похожих сигналов;
> - {ctx} #56 публичная карточка проблемы.
>
> {R-122} **Задачи**
> {R-123} ○ {R-124} 7 — {R-125} Классификация сигнала — {R-126} 3-й день
> {R-127} high · {R-128} в план · {R-129} отменить
> {R-130} ✓ 9 — Черновик карточки — {R-131} на подтверждении
> {ctx} normal · {R-132} подтвердить · {R-327} вернуть · {R-133} отменить
>
> {R-134} **GitHub** `org/sensor`: {R-135} CI зелёный · {R-136} открытых PR 2 · {R-137} milestone Pilot {R-138} до 12.10

{R-139} Процент и списки «Сделано / В работе / Далее» — issues репозитория, {R-140} короткий срез. {R-151} У issue в «В работе» стоит имя assignee — пользователь бота по `github_login`; {R-152} незаписанный логин печатается как `@login`, {R-153} несколько assignees — через запятую. {R-141} «Задачи» — то, что человек завёл в этом топике. {R-142} Кружок стоит у названия {R-154} и сам служит кнопкой: нажатие ставит галочку, {R-155} повторное нажатие до подтверждения снимает её. {R-143} На второй строке абзаца всегда стоит слово приоритета, {R-144} затем «в план» или «подтвердить», {R-328} у задачи на подтверждении — ещё «вернуть», {R-145} и «отменить».

{ctx} Процент не двигают:

- {R-146} закрытая задача;
- {R-147} галочка;
- {R-148} смерженный PR.

{R-149} Его двигает смена состояния issue.

## 2. Данные и роли

### 2.1 Проект и репозиторий

{R-156} Проект — единица людей и учёта. {ctx} У него:

- {R-157} имя;
- {R-158} описание;
- {R-159} таймзона;
- {R-160} общая супергруппа.

{ctx} По таймзоне проекта считаются:

- {R-161} «сегодня»;
- {R-162} границы суток;
- {R-163} застой.

{R-164} Час отчёта считается по таймзоне группы.

{R-165} К проекту можно подключить не больше одного GitHub-репозитория. {R-166} Один репозиторий можно подключить к нескольким проектам: {ctx} в одном репозитории работают разные команды. {ctx} У этих проектов отдельные:

- {R-167} задачи;
- {R-168} роли;
- {R-169} канвасы.

{R-170} Отчёт в командный топик группы уходит один, {R-171} блоком на каждый её проект. {R-172} Зеркало GitHub одно на репозиторий, {R-173} его читают все проекты, к которым он подключён. {R-174} Прогресс по issues тоже один на репозиторий: {R-175} у таких проектов на канвасе одна и та же доля.

{R-176} Проект без репозитория допустим. {ctx} Без репозитория работают:

- {R-177} задачи;
- {R-178} канвас;
- {R-179} блокеры по тишине.

{R-180} Процента проекта нет: {R-181} печатается **«Нет данных»**. {R-182} Строка GitHub показывает «репозиторий не подключён».

{R-183} Репозиторий подключает {R-184} и сменяет руководитель. {R-185} Смена репозитория меняет GitHub-картину {R-186} и линейку прогресса. {R-187} Задачи и люди остаются. {R-188} Уже записанные снимки не переписываются.

{R-189} Milestone — факт GitHub, {R-190} а не этап задач. {R-191} В строке GitHub на канвасе у него название {R-192} и срок. {R-193} Отдельного процента у milestone нет: {R-194} в линейку проекта входят issues всего репозитория, {R-195} а не одного milestone.

### 2.2 Задача

{R-196} Задачу создаёт человек командой `/task` в своём топике исполнителя. {ctx} Задача сама не появляется:

- {R-197} из issue;
- {R-198} из PR;
- {R-199} из коммита.

{R-200} Issue, на котором человек стоит assignee, задачей не становится.

{ctx} Поля:

- {R-201} номер внутри проекта;
- {R-202} название;
- {R-205} проект;
- {R-206} приоритет;
- {R-207} исполнитель;
- {R-208} статус;
- {R-209} дата создания;
- {R-210} дата изменения;
- {R-211} дата завершения.

{R-212} Приоритет задаёт порядок в «Плане», {R-213} в процент проекта не входит. {ctx} Нет полей:

- {R-214} «issue»;
- {R-215} «вес»;
- {R-216} «процент задачи».

{ctx} Статусы:

- {R-217} `PLANNED` — в плане, {R-218} в блоке «Задачи» не стоит;
- {R-219} `IN_PROGRESS` — стоит в «Задачах» на канвасе исполнителя;
- {R-220} `BLOCKED` — два дня в списке без галочки, {R-221} причина выясняется (см. 2.3);
- {R-222} `REVIEW` — исполнитель поставил галочку, {R-223} ждёт подтверждения руководителя;
- {R-224} `DONE` — руководитель подтвердил;
- {R-225} `CANCELLED` — делать не будем.

{R-226} Формулировка после `/task` становится названием. {R-227} Исполнитель — хозяин топика. {R-228} Приоритет по умолчанию `normal`. {R-229} Задача сразу встаёт на канвас в «Задачи» {R-230} (`IN_PROGRESS`). {R-231} Кнопка «в план» переносит её в `PLANNED` на том же канвасе. {R-232} Исполнителем может быть только `member` или `lead` этого проекта.

{ctx} Приоритет:

- {R-233} `high`;
- {R-234} `normal`;
- {R-235} `low`.

{R-236} По умолчанию `normal`. {R-237} Ставится на канвасе: {R-238} слово текущего приоритета на второй строке абзаца — кнопка, {R-239} нажатие крутит `normal` → `high` → `low` → `normal`. {R-240} То же слово есть у задачи в «Плане». {R-241} В процент оно не входит.

{R-242} Номер issue или PR, случайно написанный в названии, связью не считается. {R-243} Бот не разбирает текст задачи в ссылку на GitHub.

{R-244} Незакрытая задача с канваса не пропадает: {R-245} на следующий день она переносится на новый канвас того же исполнителя, {R-246} с пометкой, какой день идёт.

{R-247} Снять задачу может руководитель, {R-248} либо исполнитель, {R-249} пока она не `DONE`. {R-251} Перед удалением участника из проекта его незакрытые задачи снимают: {R-252} задачи без участника проекта не остаётся.

### 2.3 Блокеры и застой

{R-253} Задача в `IN_PROGRESS`, которую не отметили галочкой два дня, переходит в `BLOCKED`. {R-254} Бот пишет в топик исполнителя: «7 не двигается 3-й день, что мешает?» — {R-255} с кнопкой «нет блокера». {R-256} Текст ответа становится причиной; {R-329} ответ — это reply на вопрос бота. {R-257} Кнопка «нет блокера» возвращает задачу в `IN_PROGRESS`. {R-258} По одной задаче бот спрашивает не чаще раза в два дня.

{R-259} `PLANNED` так не блокируется: {ctx} план не обязан двигаться каждый день. {R-260} `REVIEW` застоем исполнителя не считается: {ctx} галочка уже стоит. {R-261} Если руководитель не подтверждает и не возвращает задачу дольше двух дней, бот напоминает об этом в топике исполнителя, {R-330} упоминая руководителей проекта, — {R-262} один раз за два дня.

{ctx} Поле блокера задачи:

- {R-263} **причина** — ответ исполнителя; {R-264} пока его нет, строка не печатается.

{R-267} «Влияние» по графу issues не считается: {ctx} у задачи нет issue, от которого можно было бы вывести, кто кого ждёт.

{R-268} Отдельно от задач бот показывает факты застоя репозитория. {R-269} Они не переводят задачу в `BLOCKED` {R-270} и не ссылаются на номер задачи:

- {R-271} CI основной git-ветки красный — {R-272} строка на каждом проекте этого репозитория;
- {R-273} открытый PR без движения дольше двух дней, {R-274} и его автор или запрошенный ревьюер — участник проекта;
- {R-275} у такого PR красный CI — это та же строка, {R-276} с пометкой про CI.

{R-277} Issue без коммитов, без PR и без свежих комментариев в блокеры не входит. {R-278} Число таких issues на канвас {R-279} и в отчёт не печатается.

{R-280} Один порог на всё — два дня:

- {R-281} на галочку задачи;
- {R-282} на PR;
- {R-283} на напоминание руководителю.

### 2.4 Участники и доступ

{R-284} Участник — аккаунт Telegram. {R-285} К нему можно записать логин GitHub. {ctx} Логин нужен, чтобы коммиты, PR и закрытые issues этого человека узнавались на канвасе и в отчёте. {R-286} Без логина участник ведёт задачи как обычно, {R-287} а его действия в GitHub остаются под именем логина {R-288} и к человеку в боте не приклеиваются.

{R-289} Один логин GitHub принадлежит одному пользователю бота. {R-290} В поле хранится текущий логин: {R-291} старый логин после смены ника новые факты уже не сопоставит.

{R-292} Один человек может состоять в нескольких проектах. {R-293} Роль задаётся в каждом проекте отдельно.

{R-294} Роли в MVP две:

- {R-295} `member` — исполнитель, {R-296} свой топик с канвасом;
- {R-297} `lead` — руководитель:
  - {R-298} подтверждает завершение;
  - {R-299} заводит проект;
  - {R-300} подключает репозиторий;
  - {R-301} собирает участников.

{R-302} Роли «только просмотр» в MVP нет. {R-303} Кого добавили в проект, тот ведёт задачи.

{R-304} Первый, кто нажал `/start`, — корень бота. {R-305} Он первый `lead` {R-306} и единственный, кто появляется сам. {R-307} В каждом проекте, который он заводит, он `lead`. {R-308} Остальные пользователи боту известны только после своего `/start` {R-309} и ничего не могут, пока корень или `lead` проекта не добавит их. {R-310} Второй `/start` корнем не становится.

{R-311} Бот отвечает корню и участникам проекта. {R-312} Остальным — отказ, {R-313} без раскрытия данных.

{R-314} Галочку ставит исполнитель. {R-315} Снять галочку до подтверждения может он же: {R-316} задача возвращается в `IN_PROGRESS` {R-317} и снова стоит в «Задачах» на канвасе. {R-318} Руководитель из `REVIEW` либо подтверждает `DONE`, {R-319} либо возвращает задачу в работу кнопкой «вернуть». {R-320} Если в проекте один руководитель и он же исполнитель, он подтверждает свою задачу сам. {R-321} Если руководителей несколько, свою задачу подтверждает другой руководитель.

## 3. GitHub-интеграция

{R-331} Бот читает репозиторий:

- {R-332} issues;
- {R-333} pull requests;
- {R-334} коммиты;
- {R-335} статусы CI;
- {R-336} milestones;
- {R-338} даты;
- {R-339} логины авторов.

{R-340} Git-ветки {R-341} и метки сами по себе на канвас и в отчёт не выводятся.

{R-342} Доступ — через **GitHub App**, {R-343} не через личный токен: {ctx} приватные репозитории, секрет для webhooks, отдельные лимиты.

{R-344} Обновление — webhooks:

- {R-345} `push`;
- {R-346} `pull_request`;
- {R-347} `issues`;
- {R-348} `workflow_run`;
- {R-436} `milestone`;
- {R-437} события sub-issues;
- {R-438} события связей `blocked by`.

{R-350} Опрос только догоняет пропущенную доставку.

{R-351} **Синхронизация односторонняя:** GitHub → бот. {ctx} Issues, PR, assignees, метки и комментарии меняет человек в GitHub. {R-352} Бот туда не пишет.

{R-353} Зеркало хранится на репозитории. {R-354} Проект его не копирует себе. {R-355} Два проекта с одним репозиторием видят одни и те же объекты GitHub; {R-356} различается только то, какие из них относятся к участникам данного проекта (см. 3.2).

### 3.1 Что видно из зеркала

{R-357} На канвасе, если репозиторий подключён, — одна строка:

- {R-358} состояние CI основной git-ветки;
- {R-359} число открытых PR;
- {R-360} ближайший открытый milestone {R-361} с датой.

{R-362} Процента у milestone нет. {R-363} Нет даты — строка milestone не печатается. {R-364} CI неизвестен — на этой строке «Нет данных», {R-365} и это не блокер. {R-366} Отдельного экрана GitHub нет.

{ctx} В зеркале лежат:

- {R-367} CI;
- {R-368} открытые PR;
- {R-369} смерженные PR;
- {R-370} хвост коммитов;
- {R-371} issues;
- {R-372} milestones.

{R-374} На канвас из этого выходит одна строка. {R-375} В блокеры — красный CI {R-376} и застоявшиеся PR участников. {ctx} В отчёт:

- {R-377} CI;
- {R-378} число смерженных PR;
- {R-379} число коммитов;
- {R-380} имена проектов этого репозитория.

{ctx} В чат не вываливается полный список:

- {R-381} PR;
- {R-382} коммитов;
- {R-383} issues.

{R-384} Связи `blocked by` {R-385} и sub-issues хранятся в зеркале {R-386} и дописываются к issue, который и так попал в срез канваса. {R-387} Очередь плана от них не зависит.

### 3.2 Чьи это факты

{R-388} Факт GitHub попадает на проект по двум правилам.

{ctx} **Общие для репозитория.** {R-389} Красный CI основной git-ветки виден каждому проекту, к которому подключён этот репозиторий. {R-390} Зелёный CI отдельной строкой в блокеры не пишется.

{ctx} **Личные.** {R-391} Коммит, PR и закрытый issue относятся к участнику, если логин действующего лица совпал с `github_login`. {ctx} Учитываются:

- {R-392} для PR — автор {R-393} и запрошенный ревьюер;
- {R-394} для коммита — автор;
- {R-395} для закрытого issue — кто его закрыл.

{R-396} Такой факт виден проектам, где этот человек участник и куда подключён этот репозиторий.

{R-397} Логин, который не совпал ни с одним участником проектов этого репозитория, в блокеры не поднимается. {ctx} Иначе чужой PR стал бы блокером обеих команд. {R-398} В строке GitHub он может остаться только как автор в зеркале, {R-399} отдельной строкой на канвасе его нет.

{R-400} Один и тот же PR не дублируется внутри одного проекта, {R-401} даже если и автор, и ревьюер состоят в нём. {R-402} В двух проектах, где состоит один и тот же автор, строка будет в обоих: {ctx} человек участвует в обоих.

### 3.3 Расхождение учёта

{R-403} Прогресс проекта считается по issues. {ctx} Задачи — другой слой: день, галочка, подтверждение. {R-404} Работа, которую не завели задачей, на канвас в блок «Задачи» не попадает. {ctx} Это нормальная граница, а не дыра, которую надо закрыть импортом issues в задачи.

{R-405} Сигнал расхождения — проектный, {R-406} за календарные сутки по таймзоне проекта. {R-407} Он загорается, когда одновременно:

- {R-408} в репозитории есть коммит, {R-409} смерженный PR {R-410} или закрытый issue, {R-411} и логин действующего лица совпал с участником **этого** проекта;
- {R-412} в проекте за те же сутки не создана ни одна задача {R-413} и ни одна не перешла в `DONE`.

{R-414} Текст: «В репозитории есть движение, в задачах за сутки тишина».

{R-415} Сигнал не меняет статусы {R-416} и не создаёт блокер. {R-417} Движение чужой команды в том же репозитории этот проект не тревожит. {R-418} Красный CI расхождением не считается: {ctx} это не сделанная работа, а сломанная проверка.

### 3.4 Где человек стоит в бэклоге

{R-419} Место человека в проекте читается по issues, {R-420} а не по задачам бота.

{R-421} Issue относится к пользователю, если среди его assignees есть `github_login` этого пользователя. {R-422} Логин сопоставляется с аккаунтом Telegram в момент показа. {R-423} Задача из этого не создаётся, {R-424} статус задачи не меняется, {R-425} процент проекта не делится по людям.

- {R-426} **Сделал** — такие issues закрыты как сделанные (`completed`).
- {R-427} **Сейчас** — такие issues ещё открыты. {ctx} Это и есть «где он сейчас» в бэклоге.
- {R-428} **Дальше** — остальные открытые issues того же репозитория: {ctx} они ещё не на нём.

{R-429} Без логина этого среза нет: {R-430} строка человека печатается как «нет сопоставления с GitHub». {R-431} Задачи при этом работают.

{R-432} Один issue с несколькими assignees входит в «сейчас» каждого совпавшего участника {R-433} и в процент проекта — один раз. {R-434} Чужой логин, не записанный ни на кого в боте, в строке человека на канвасе не появляется.

## 4. Расчёт прогресса

Линейка — репозиторий проекта, не набор задач, которые люди завели по ходу дня. В GitHub бэклог расписан целиком, в боте задач мало, и они закрываются почти сразу. Процент по задачам поэтому почти всегда высокий и почти только растёт. Процент по issues ведёт себя иначе: полный бэклог с самого начала стоит в знаменателе, новая незакрытая работа процент снижает.

`прогресс = issues completed / (открытые + completed)`

Каждый issue весит одинаково. Размер работы внутри issue бот не оценивает. Поэтому рядом с процентом всегда печатается остаток: **осталось 18 из 31**. Высокие 90% без остатка прячут хвост бэклога, остаток его показывает.

В числителе только `completed`. Открытый issue стоит в знаменателе, кем бы он ни был назначен. Issue, закрытый как `not_planned`, не стоит ни там, ни там: снятая работа не раздувает процент. Смерженный PR и закрытая задача бота в формулу не входят.

Если репозиторий не подключён или в формуле пустой знаменатель, процента нет: печатается **«Нет данных»**, не 0%.

У двух проектов с одним репозиторием процент совпадает: бэклог общий. Делёж issues одного репозитория по проектам в эту формулу не входит.

Общий процент считается той же формулой по issues репозиториев, каждый репозиторий один раз. Проект без репозитория в общую цифру не входит. Это доля закрытого бэклога, а не среднее арифметическое карточек. Строка «все проекты» есть и в личке, и в командном топике.

Снимок пишется раз в сутки по таймзоне проекта и хранит эту долю. Из снимков строится динамика. Пропуски не заполняются соседними числами. Смена репозитория старые снимки не переписывает.

## 5. Канвас

Канвас — то самое сообщение из раздела 1. Оно живёт в топике исполнителя. Личка бота канвас не дублирует и меню не показывает. Бот правит одно сообщение, второе на те же сутки не создаёт. Как задача на него попадает — в разделе 6.

Состав, сверху вниз:

- дата и имя проекта;
- доля бэклога и остаток открытых issues (раздел 4);
- строка этого человека по 3.4;
- **Сделано** — до пяти последних issues `completed`;
- **В работе** — до пяти открытых issues, у которых есть assignee;
- **Далее** — до пяти открытых issues без assignee;
- **Задачи** — его `IN_PROGRESS`, `BLOCKED` и `REVIEW`. Название с днём на первой строке абзаца, действия — на следующей. Номера issue и PR нет;
- **План** — его `PLANNED`. Сначала больший приоритет, внутри одного приоритета раньше созданная выше. Пустой план не печатается;
- **Блокеры** — причины его задач в `BLOCKED` и его строки CI / PR из 2.3. Чужой PR сюда не входит. Красный CI основной git-ветки — отдельная строка;
- **GitHub** — одна строка из 3.1, либо «репозиторий не подключён»;
- **Динамика** — последние снимки доли одной строкой: `10.09 — 31% · 17.09 — 42%`.

Если за сутки сработало расхождение из 3.3, его строка стоит под GitHub.

Подтверждённая задача с канваса уходит. В блоке «Задачи» она больше не висит. Дата подтверждения остаётся в отчёте.

### 5.1 Настройки

Имя проекта, описание, таймзона проекта, супергруппа, участники и роли, топик исполнителя, командный топик, логин GitHub, подключённый репозиторий, время отчёта группы. Как это проходит в первый раз — в 5.2.

Смена таймзоны не переписывает уже отправленный канвас. Новые сутки и новый застой считаются по новой зоне.

### 5.2 Онбординг

#### Первый пользователь

Пока в боте никого нет, первый `/start` создаёт корня. Бот пишет, что он руководитель и может завести проект. Позже `/start` только запоминает аккаунт Telegram и говорит, что доступ появится, когда руководителя добавят в проект.

#### Новый проект

Проект заводит корень или `lead`. Делает это в личке бота.

1. «Новый проект»: имя, описание, таймзона.
2. Бот просит супергруппу с темами и права администратора: сообщения и управление темами.
3. Когда бота добавили, руководитель подтверждает супергруппу. Если к ней уже привязан другой проект, новый садится в ту же группу и тот же командный топик. До привязки канвас и отчёты некуда отправлять.
4. Репозиторий — отдельный шаг, его можно пропустить. Бот показывает репозитории установки GitHub App. Подключает и меняет только руководитель.
5. Бот спрашивает, есть ли уже командный топик. Если есть — руководитель указывает его. Если нет — бот создаёт топик «Отчёты». Затем спрашивает время ежедневной отправки. Пока время не названо, расписание выключено. Команда `/report` в группе уже отвечает.

#### Участник

1. Человек входит в группу проекта.
2. Открывает бота в личке и отправляет `/start`. Бот запоминает аккаунт Telegram.
3. Корень или `lead` проекта видит людей, которые уже нажали `/start` и ещё не в проекте, и добавляет их как `member`.
4. Бот спрашивает у человека логин GitHub. Шаг можно пропустить и заполнить позже. Логин один на пользователя бота, не на каждый проект.
5. Бот сначала спрашивает, есть ли у человека топик в группе. Если есть — руководитель указывает его, бот ставит туда канвас. Если нет — бот создаёт топик с именем человека и ставит канвас туда. В топик пишет, что задача заводится командой `/task` в этом топике.

Пока супергруппа не привязана, топик исполнителя пуст: канвас появится после привязки.

#### Первое сообщение сотруднику

Одним текстом в личку и тем же текстом в его топик:

- где его топик и канвас;
- задача заводится командой `/task` в этом топике, она появляется на канвасе;
- галочка отправляет задачу руководителю и процент проекта не меняет;
- место в бэклоге — issues, где он assignee; без логина GitHub этой строки нет.

## 6. Как задача попадает на канвас

Канвас — rich message (`sendRichMessage`), бот правит его на месте. Действия — кнопки внутри абзаца задачи (`RichTextButton`, `callback_data`), стиль `link`. Клавиатуры под сообщением нет. Ряда кнопок (`tg-button-row`) нет. На телефоне в одну строку не влезает: первая строка абзаца — отметка, номер, название и какой день, вторая — слово приоритета, затем «в план» или «подтвердить», у задачи на подтверждении — ещё «вернуть», и «отменить».

Галочка `- [ ]` в rich message — рисунок: у неё нет `callback_data`, нажатие боту не приходит. Отмеченным пункт становится после callback, когда бот перерисовал строку.

`sendChecklist` не используем: он требует Business-аккаунт и не работает в топиках супергруппы. Issues, PR и CI кнопками не закрываются. Лимит rich message — 32768 символов и 500 блоков. В топик сообщение уходит с `message_thread_id`.

Канвас свой у каждого исполнителя: пара «проект + исполнитель + дата» — не больше одного сообщения. Дата — по таймзоне проекта. Топик есть и у `member`, и у `lead`.

Человек пишет в свой топик команду `/task <формулировка>`. Бот заводит задачу и дописывает её строкой в блок «Задачи» того же канваса. Чужие топики задачу ему не создают. Шага «выберите issue» нет.

- канваса на сегодня нет — новое сообщение;
- уже есть — правка того же сообщения;
- текст не помещается в лимит rich message — сначала ужимаются срезы issues, блокеры и динамика. Задачи не выкидываются. Если не влезают уже они, бот отказывает: канвас заполнен. Второе сообщение на ту же дату не создаётся.

Незакрытые задачи (`IN_PROGRESS`, `BLOCKED`) на следующий день переносятся на новый канвас, с пометкой, какой это день. `REVIEW` назавтра остаётся на канвасе отмеченной, пока руководитель не ответит. `PLANNED` переносится в блок «План» без кнопки галочки.

Галочка переводит задачу в `REVIEW`. `DONE` ставит руководитель по правилу из 2.4, кнопкой на этом же канвасе. Пока он не ответил, процент проекта прежний.

«Отменить» в строке задачи переводит её в `CANCELLED`. Нажимает исполнитель или руководитель, пока задача не `DONE`. После этого строка с канваса уходит и на следующий день не переносится. Процент проекта от этого не меняется.

Передача исполнителя убирает пункт с канваса прежнего и ставит на канвас нового, если задача была `IN_PROGRESS` или `BLOCKED`.

## 7. Отчёты

### 7.1 Ежедневный

Отчёт — что изменилось за сутки, не второй канвас. Доля и остаток — из раздела 4. Закрытые issues и задачи не смешиваются.

В личке — проекты этого человека. В командный топик тем же составом уходят сразу все проекты этого чата: строка «все проекты» и блок на каждый. Топики исполнителей отчёт не получают.

> **За сутки · 17.09**
> **Все проекты:** 37% → 39% · осталось 41 из 67
>
> **Общественный сенсор**
> **Бэклог:** 42% → 45% · осталось 17 из 31
> Закрыто: #11 Telegram-интерфейс
> Открыто новых: 1
>
> **Задачи:** подтверждено 1 · создано 2 · отменено 0 · встало в блок 1
> Сейчас: 7 — Классификация сигнала — Андрей, 3-й день
> Дальше: 14 — Подготовить тестовые данные
> Риск: нет стабильного доступа к одному из источников данных
>
> **GitHub** `org/sensor`
> CI зелёный · смержено PR 1 · коммитов 6
> Проекты: Общественный сенсор

«В репозитории есть движение, в задачах за сутки тишина» печатается в блоке того проекта, для которого условие из 3.3 выполнено.

В личном отчёте «Сейчас» и «Дальше» — задачи этого человека. В командном топике — задачи всех участников этих проектов, с именем. Блок GitHub один на репозиторий, даже если им пользуются два проекта. Закрытые issues в него не копируются: они уже в «Бэклоге».

### 7.2 Еженедельный

Тот же состав за семь суток. В командный топик он тоже уходит целиком, со строкой «все проекты» и блоком на каждый проект чата.

> **За неделю · 11.09–17.09**
> **Все проекты:** было 24% → стало 37% · осталось 41 из 67
>
> **Общественный сенсор**
> **Бэклог:** было 28% → стало 42% · осталось 18 из 31
> Закрыто: 13, среди них #4 архитектура проекта, #8 структура базы данных
>
> **Задачи:** подтверждено 6 · создано 9 · отменено 1
> Что замедлило: нет стабильного доступа к одному из источников данных. PR #138 без движения 4 дня, CI красный
> Дальше: 14 — Подготовить тестовые данные
>
> **GitHub** `org/sensor`
> коммитов 47 · PR смержено 8

Коммиты и PR в долю бэклога не входят и в сумму по проектам не складываются. Один репозиторий на неделе печатается один раз.

### 7.3 Откуда берутся строки

Их никто не пишет вручную.

- **Бэклог** — доля и остаток на начало и конец периода. «Закрыто» — issues, ставшие `completed`. «Открыто новых» — issues, созданные за период и всё ещё открытые. `not_planned` в эти строки не входит.
- **Задачи** — счётчики за период: перешли в `DONE`, созданы, перешли в `CANCELLED`, впервые стали `BLOCKED`. Это задачи, не коммиты.
- **Сейчас** — `IN_PROGRESS` и `BLOCKED`. В личке только этого человека, в командном топике все участники проектов этого отчёта. Нет таких — строка не печатается.
- **Дальше** — до трёх задач `PLANNED`: сначала больший приоритет, внутри него раньше созданная. В личке план этого человека, в командном топике планы участников.
- **Риск** и **Что замедлило** — причины блокеров задач и факты из 2.3, дословно.
- **GitHub** — CI, смерженные PR и коммиты репозитория. Названия issues сюда не подмешиваются.

Нет данных — строка не печатается. Пустой процент не заменяется нулём. Списки длиннее пяти пунктов не вываливаются: печатается число и до пяти названий.

### 7.4 Доставка

Отчёт читают в двух местах.

- **В личке бота** — `/report` в любой момент. Карточки проектов пользователя и блоки их репозиториев, со строкой «все проекты».
- **В командный топик** — по расписанию, и по `/report` из группового чата. Туда одним сообщением уходят все проекты этого чата, со строкой «все проекты». Топики исполнителей этот отчёт не дублируют.

Командный топик не совпадает с топиками исполнителей и хранится отдельно. Время и включение рассылки задаются на чат, не на каждый проект. Личный `/report` работает и при выключенной рассылке. Пока командный топик не задан, `/report` из группы отвечает в том чате, откуда его вызвали. Недельный отчёт идёт туда же, целиком.

```

                                             ├── Tasks
                                             ├── GitHub mirror (на репозиторий)
                                             ├── Event Processor
                                             └── Report Generator
GitHub: API + Webhooks → Event Processor
```

Задачи с зеркалом не соединены внешним ключом. Сопоставление человека и логина происходит в момент показа.

## 9. Структура данных

Сначала люди и чат, потом проекты и задачи, потом канвас, в конце зеркало репозитория. Задача на issue не ссылается.

### users

`id`, `telegram_user_id`, `github_login` (пусто — сопоставления нет), `name`, `is_root`

`telegram_user_id` уникален. Пустой логин уникальности не нарушает, занятый логин — один на бота. `is_root` истинен ровно у одного пользователя: того, кто первым нажал `/start`.

### chats

`id`, `telegram_chat_id` — супергруппа, не топик, `reports_topic_id` — командный топик внутри этой группы (пусто — не выбран), `timezone`, `daily_cron`, `weekly_cron`, `daily_enabled`, `weekly_enabled`

Топик исполнителя здесь не хранится: он в `project_members.topic_id`. Расписание отчётов живёт на группе, не на проекте. В `reports_topic_id` уходит один отчёт сразу по всем проектам этой группы.

### projects

`id`, `chat_id`, `name`, `description`, `repository_id` (пусто — репозиторий не подключён), `timezone`, `created_at`

Несколько проектов могут ссылаться на один `chat_id` и на один `repository_id`. Сутки задач и застой считаются по таймзоне проекта. Час отчёта — по таймзоне чата.

### project_members

`id`, `project_id`, `user_id`, `role` (`member` / `lead`), `topic_id` — топик исполнителя; пусто, пока чат не привязан

Уникально `project_id + user_id`. Канвас живёт в `topic_id`. Командный топик сюда не пишется.

### tasks

`id`, `project_id`, `number`, `title`, `status` (`PLANNED` / `IN_PROGRESS` / `BLOCKED` / `REVIEW` / `DONE` / `CANCELLED`), `priority` (`high` / `normal` / `low`), `assignee_id`, `created_at`, `updated_at`, `completed_at`

`number` уникален в проекте. Колонок issue и прогресса задачи нет. Вес не хранится.

### blockers

`id`, `task_id`, `reason`, `asked_at`, `resolved_at`

Только блокеры задач. Строки про CI и PR сюда не пишутся: они выводятся из зеркала.

### canvases

`id`, `project_id`, `assignee_id`, `topic_id`, `message_id`, `canvas_date`

Одно rich-сообщение канваса. Уникально `project_id + assignee_id + canvas_date`.

### canvas_items

`id`, `canvas_id`, `task_id`, `position`, `carried_from_canvas_id`

Какие задачи нарисованы на этом канвасе и в каком порядке. Галочка, «в план», «подтвердить» и «отменить» в таблицу кнопок не складываются: их рисуют из `tasks.status`.

### repositories

`id`, `owner`, `name`, `default_branch_ci`

### issues

`id`, `repository_id`, `issue_number`, `title`, `state`, `state_reason` (`completed` / `not_planned`, пусто у открытого), `closed_by_login`, `updated_at`, `closed_at`

Природный ключ — репозиторий и номер, не проект. Из этой таблицы считается доля бэклога.

### issue_assignees

`issue_id`, `login` — зеркало assignees. Один issue может быть назначен нескольким людям. По этим логинам строится срез 3.4.

### issue_dependencies

`issue_id`, `depends_on_issue_id`, `link_type` (`blocked_by` / `sub_issue`) — дописывается к issue, который и так попал в срез канваса

### milestones

`id`, `repository_id`, `milestone_number`, `title`, `state`, `due_on` — зеркало GitHub, не этапы проекта. Отдельного процента нет.

### pull_requests

`id`, `repository_id`, `pull_request_number`, `title`, `author_login`, `state`, `ci_status`, `updated_at`, `merged_at`, `merged_by_login`

### commits

`id`, `repository_id`, `sha`, `message`, `author_login`, `created_at` — хвост для строки GitHub на канвасе и блока отчёта, не журнал всей истории

### progress_snapshots

`id`, `project_id`, `progress`, `created_at`

Суточная доля бэклога проекта. У двух проектов с одним репозиторием числа совпадают. Смена репозитория старые строки не переписывает.

### events

`id`, `source`, `event_type`, `payload`, `created_at` — журнал только дополняется

---

## 10. AI-слой

AI может пересказать уже собранные блоки отчёта обычным языком и заметить расхождение из 3.3 теми же фактами.

AI не является источником истины. Он не заводит задачи, не ставит `DONE`, не придумывает связь задачи с issue и не добавляет фактов, которых нет в задачах и в зеркале.

---

## 11. Definition of Done

Задача проекта выполнена, когда руководитель подтвердил её по правилу из 2.4 и у неё нет открытого блокера.

Смерженный PR, закрытый issue и зелёный CI таким подтверждением не являются.

## 12. Объём работ

### MVP

1. {R-001} Канвас в топике исполнителя; {R-002} несколько проектов на одном репозитории; {R-003} проект может быть без репозитория. {R-004} Меню в личке нет.
2. {ctx} Участники и доступ:
   - {R-005} участники;
   - {R-006} роли;
   - {R-007} доступ по составу проекта;
   - {R-008} логин GitHub у человека.
3. {R-009} Задачи со статусами {R-010} и приоритетом, {R-011} без связи с issue.
4. {R-012} Прогресс проекта — доля `completed` issues репозитория {R-013} и остаток открытых. {R-014} Задачи и галочка этот процент не двигают. {R-015} Место человека в бэклоге — по assignees и `github_login`.
5. {ctx} На канвасе:
   - {R-016} доля бэклога;
   - {R-017} срез issues;
   - {R-018} задачи с кнопками в строке;
   - {R-019} план;
   - {R-020} блокеры;
   - {R-021} строка GitHub;
   - {R-022} короткая динамика.
6. {R-023} Блокировка задачи через два дня {R-024} и вопрос исполнителю; {R-322} напоминание руководителям о задаче на подтверждении; {R-025} отдельно — CI {R-026} и застоявшиеся PR участников.
7. {R-027} Задача создаётся командой `/task` в топике исполнителя {R-028} и попадает на канвас. {R-029} Незакрытое переносится на следующий день.
8. {R-030} Ежедневный отчёт в личке — проекты этого человека. {R-031} В командный топик одним сообщением — все проекты группы, {R-032} по `/report` {R-033} и по расписанию. {R-034} GitHub — блоком на репозиторий.
9. {ctx} Онбординг:
   - {R-035} первый `/start` создаёт корня;
   - {R-036} новый проект;
   - {R-037} привязка супергруппы;
   - {R-038} привязка репозитория;
   - {R-039} командный топик;
   - {R-040} добавление участника;
   - {R-041} логин GitHub;
   - {R-042} топик исполнителя с канвасом.
10. {R-043} Webhooks GitHub App как основной канал, {R-044} опрос — только сверка пропущенного.
11. {R-045} Строка расхождения «в репозитории есть движение, в задачах тишина».

{ctx} Не входит в MVP:

## 13. Критерий успеха

> Насколько быстро человек понимает состояние разработки, не открывая GitHub и не спрашивая разработчиков.

Целевое поведение: **открыл свой топик → за 10–20 секунд по канвасу понял, какая доля проекта уже сделана и сколько issues осталось, где в бэклоге стоит человек, какие задачи на нём сегодня и что блокирует работу.** Картина репозитория — одна строка рядом. Задачи остаются учётом дня и процент проекта не подменяют.
