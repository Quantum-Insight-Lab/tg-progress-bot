> Архитектурный шаблон PDA (разделы 4, 6). Инварианты и граф домена в центре, интерфейсы и инфраструктура — на периферии.

# Архитектура

## Компоненты

| Компонент PDA | Наш модуль | Содержание |
| --- | --- | --- |
| Uncertainty Layer | `src/telegram` | экраны, меню, инлайн-кнопки, список дня, вопросы бота — реализация актов из [02](02-certainty-acts.md) |
| Domain Layer | `src/domain` | Task, Blocker, Project, переходы статусов, валидаторы инвариантов, расчёт веса |
| Event Core | `src/events` | журнал append-only, публикация, идемпотентность, генерация типов из реестра |
| Read Models | `src/projections` | проекции из [06](06-events.md), пересобираемые из журнала |
| Integration Layer | `src/github` | GitHub App, webhooks плюс редкий опрос-сверка, зеркало issues, PR, CI, milestones |
| Observability | `src/observability` | метрики из [08](08-observability.md), доменные инциденты |
| Stability Engine | не выделен | устойчивость здесь сводится к идемпотентности и лимитам; отдельный компонент без анти-абуза и экономики был бы пустым (см. [00](00-README.md)) |

## Поток данных

```
Telegram (акты A-1…A-10)        GitHub (факты A-11, A-12)
        │                                │
        v                                v
 [src/telegram]                    [src/github]
        │  команда                       │  внешний факт + delivery_id
        v                                v
                  [src/domain]
        валидаторы, переходы статусов, права
                        │  событие
                        v
                  [src/events]          append-only, idempotency_key
                        │
        ┌───────────────┼────────────────┐
        v               v                v
 [src/projections]  [планировщик]  [src/observability]
  экраны, отчёты    A-13…A-16        метрики, инциденты
```

Направление жёсткое: команда не может стать фактом, минуя домен, а проекция не может записать факт (S-5). Планировщик — обычный источник команд, он тоже проходит через домен.

## Слои и границы

Разрешённые зависимости, они же конфиг для проверок S-1 и S-2:

```
telegram   → domain, projections, events(types)
github     → domain, events(types)
domain     → events(types)
projections→ events(types), db(read)
events     → db
observability → всё, только чтение
```

Запрещено: `domain → telegram`, `domain → github`, `domain → projections`, любые импорты между `telegram` и `github`, обращение проекций к домену.

Контексты из [03](03-domain-graph.md) живут внутри `src/domain` отдельными каталогами (`projects`, `tasks`) и общаются событиями, а не прямыми вызовами, — даже при одном исполнителе это то, что не даёт AI-агенту срастить модули.

## Решения и их причины

| Решение | Причина |
| --- | --- |
| Один процесс, планировщик внутри | нагрузка — десятки событий в день; брокер и вторая единица развёртывания добавили бы отказов больше, чем убрали |
| Журнал в PostgreSQL, не в брокере | нужен не транспорт, а воспроизводимость: журнал читается запросами и переигрывается в проекции |
| Проекции в тех же таблицах БД, без отдельного хранилища | объём данных мал; ценность проекций здесь в разделении записи и чтения, а не в скорости |
| GitHub — webhooks с первого дня, опрос только сверка | бот и так слушает входящий HTTP (Telegram webhook); GitHub App даёт подпись и `delivery_id` для INV-08. Постоянный опрос дублирует то, что уже приходит событиями, и создаёт лаг. Интервал сверки — C-6 |
| Расчёт прогресса — функция, а не поле | поле пришлось бы поддерживать при каждом изменении задачи; функция всегда согласована, а история живёт в снимках |
| Идемпотентность на уровне БД | уникальный индекс работает и при гонке двух обработчиков, проверка в коде — нет |
| Таймзона проекта — параметр каждой операции с датами | «сегодня» не существует в вакууме; функция без явной таймзоны создаёт ошибку на границе суток, которую невозможно отловить в тестах в другом часовом поясе |

## Пересборка проекций

Любая проекция восстанавливается из журнала одной командой: `scripts/rebuild-projection.ts <name>`. Это требование воспроизводимости из PDA 4.1 и одновременно способ исправлять ошибки в логике проекций без миграций данных.

Что должно быть верно, чтобы пересборка работала: события полны сами по себе. В `payload` кладутся все поля, нужные для проекции, а не только идентификаторы — иначе восстановление зависит от текущего состояния таблиц, и смысл журнала теряется.

## Развёртывание

Docker-образ, переменные окружения читаются только в `src/config`. Секреты: токен бота, приватный ключ GitHub App, строка подключения к БД, секрет webhook. Миграции применяются при старте отдельным шагом, а не самим приложением.
