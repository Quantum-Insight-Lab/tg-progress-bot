# Контракт исполнителя

Читается перед каждой задачей. Основание: PDA v1.1, патч v1.2 раздел 9.5.
Документация домена: [`docs/pda/`](docs/pda/00-README.md). Требования к продукту: [`Прогресс-бот.md`](docs/archive/Прогресс-бот.md).

Этот файл снижает частоту нарушений, обнуляют их проверки в CI ([`docs/pda/09`](docs/pda/09-structural-invariants.md)). Если правило отсюда не подкреплено проверкой, оно всё равно обязательно к соблюдению, но считается менее надёжным.

## Карта слоёв

```
src/telegram   → domain, projections, events(types)
src/github     → domain, events(types)
src/domain     → events(types)          ← законы живут здесь
src/projections→ events(types), db(read)
src/events     → db
src/config     ничего не импортирует из src
```

Запрещено: `domain → telegram`, `domain → github`, `domain → projections`, импорты между `telegram` и `github`, обращение проекций к домену, запись из проекций в журнал.

Внутри `src/domain` контексты `projects` и `tasks` не импортируют друг друга: связь только через события.

## Реестр механизмов

## Запреты

1. **Новый `event_type` без записи в `contracts/event-registry.yaml`.** Литерал типа события в коде запрещён.
2. **Правка схемы существующего события.** Только `version + 1`: в журнале уже лежат факты.
3. **Доменное правило вне `src/domain`.** Проверка роли, перехода статуса, условия блокировки в хендлере Telegram — нарушение, даже если работает.
4. **Числовой порог в коде домена.** Всё из `src/config` (S-8).
5. **`new Date()` и `Date.now()` в домене.** Только `clock` (S-10).
6. **Любая мутация в GitHub.** Ни создания issue, ни закрытия, ни смены assignee, ни комментариев: интеграция односторонняя (INV-09).
7. **Новая зависимость без согласования.** Пакет добавляется отдельным коммитом с обоснованием.
8. **Обход проверки доступа.** Хендлеры регистрируются через фабрику, навешивающую guard; ручная регистрация запрещена (INV-12).
9. **Запись в таблицу `events`, кроме как через `emit`.** Журнал только дополняется (INV-16).
10. **Отключение или ослабление проверки в CI, чтобы прошла своя задача.** Если проверка мешает — останов и запрос решения.

## Порядок работы

1. **Сначала спека, потом код.** Задача начинается с ответа на вопрос, какую неопределённость из [`docs/pda/01`](docs/pda/01-uncertainty-map.md) она закрывает и какие инварианты затрагивает.
2. Если задача требует нового события, сущности, связи или перехода статуса — сначала правка `docs/pda/` и `contracts/`, отдельным коммитом, затем реализация.
3. Реализация: домен → события → проекции → интерфейс. В обратном порядке правила расползаются по хендлерам.
4. Тесты на затронутые инварианты пишутся в той же задаче, а не «потом».
5. Перед сдачей — весь набор проверок локально: типы, линтер, границы, генерация событий, сверка инвариантов, тесты.

## Definition of Done инженерной задачи

- код реализован, типы проходят без `any` в домене;
- для каждого затронутого инварианта есть тест, имя которого начинается с его ID;
- реестр событий обновлён, сгенерированные типы закоммичены и совпадают с результатом повторной генерации;
- если менялись пороги или коэффициенты — обновлена соответствующая Constant Card в [`docs/pda/05`](docs/pda/05-constants.md);
- если появился новый механизм — обновлён реестр механизмов в этом файле;
- все проверки CI зелёные, ни одна не отключена и не переведена в предупреждение;
- поведение сверено с ТЗ; расхождение либо исправлено в коде, либо зафиксировано правкой ТЗ, но не оставлено молча.

Продуктовое определение готовности задачи (подтверждение руководителем) — другое и описано в ТЗ, раздел 11.

## Что делать при конфликте

Остановиться и запросить решение, не изобретать, если:

- задача требует расширить граф домена: новую сущность, связь или переход статуса;
- требуется новое событие, а его место в реестре неочевидно;
- инвариант из [`docs/pda/04`](docs/pda/04-invariants.md) мешает выполнить требование ТЗ — это означает, что расходятся два источника, и выбирать между ними не дело исполнителя;
- проверка в CI блокирует изменение, которое кажется правильным;
- требование ТЗ невозможно выполнить средствами Telegram Bot API или GitHub API.

Формат запроса: что требовалось сделать, какое правило мешает, два возможных решения с последствиями. Молча достроенный домен — худший из вариантов: он проходит ревью и всплывает через месяц.
